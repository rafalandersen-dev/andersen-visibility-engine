## Auth-email admission — source-order correction (Claude, 19 September 2026)

Under the 19 September owner working agreement (Claude implements/tests/documents, Codex reviews/releases), the auth-email admission finding was corrected: source/action counters are now checked **before** the shared recipient counters. Previously the loop incremented recipient counters first, so a source already over its own quota could still mint recipient rows for a spread of fresh names and consume a known recipient's minute/hour allowance before its own source rejection fired. With the reorder, an over-quota source is rejected at the source counter and never issues a recipient RPC. The documented tradeoff — every attempt now spends the (bounded 3/min, 20/hr) source budget before the recipient counter is consulted — is accepted as the smaller risk than cross-recipient counter poisoning. Separate per-action recovery quota and shared recipient semantics are preserved; no shared global/all-users bucket exists.

Changed files (this correction):

- `src/lib/auth-email-admission.server.ts` — reordered `RULES` (source-minute, source-hour, then recipient-minute, recipient-hour); updated the module header and rule comments to state the source-first order and the tradeoff. Loop, keying (per-action source, shared recipient), HMAC, fail-closed source canonicalization and thresholds otherwise unchanged.
- `src/lib/auth-email-admission.server.test.ts` — updated order/key/threshold expectations to the new RPC sequence (source keys are calls 0–1, recipient keys calls 2–3; inclusive-limit and over-limit-per-call rows remapped) and added one stateful regression: exhaust a source's minute quota, fire many fresh recipient names, assert the shared recipient rows are byte-for-byte unchanged, then confirm a different source can still request one of those names and the exhausted source's recovery quota still admits.
