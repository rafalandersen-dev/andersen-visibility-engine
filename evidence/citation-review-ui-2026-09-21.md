## Bounded packet (this branch)

Owner-facing review management + assigned-reviewer flow, all on existing endpoints. New files only; no edit to applied P1/P2/P3 SQL, no schema/endpoint change.

1. **Owner finding list + detail** (`CitationReviewPanel`, owner mode): list from `readCitationFindingsFn` with honest status chips (family, decision, `sourceAvailable`, `accuracyStatus`, `reviewStatus`) and an honest empty state; select → `getCitationFindingFn` detail showing the genuine record (or the legacy/malformed raw record when `recordValid:false`), live accuracy resolution and `evidenceErased`. Owner-only lists/private facts/artifacts stay owner-only.
2. **Explicit finding-scoped grant/revoke** to an ACTUAL eligible team member: the reviewer dropdown is built from `readProjectTeamRosterFn` filtered to `active`, non-expired, role `reviewer`/`editor`, `actorId !== ownerId` (candidate list; the server is authoritative and re-checks the exact policy). Before granting, a **"what will be shared"** disclosure lists exactly what the reviewer will and will not see. No auto-assignment; grant/revoke is one explicit owner action each.
3. **Assigned reviewer detail / decision / withdrawal** (reviewer mode): `getCitationFindingForReviewFn` renders the masked-safe record (`record:null` → honest "evidence withheld", never a fabricated body), the cited evidence availability, dated accuracy facts, `inspectionComplete`, live `reviewStatus`, and the `recordSha256` the reviewer pins. Decision submit via `saveCitationFindingReviewFn`; withdrawal via `removeCitationFindingReviewFn`. **Guards (pure, tested in `citation-review-ui.ts`):** approve is disabled when the record is masked (`record:null`) or `inspectionComplete` is false (no approval of unseen/uninspectable evidence); a `citation_review_stale`/`conflict` result prompts a **refresh** (re-read the current hash) rather than a blind retry; a revoked/expired/removed reviewer read fails closed server-side and surfaces the generic unavailable state.
4. **Current status vs historical receipt distinct.** The live `reviewStatus`/`inspectionComplete`/`verificationStatus` are labelled "current"; a stored receipt's `inspectionComplete` and decision are labelled "recorded at the time" and never re-counted. `owner_attested` is shown as an owner attestation, explicitly not independent/cause proof.

## Acceptance / tests (this packet — deterministic, offline)

Pure guard/eligibility logic in `citation-review-ui.ts`, tested in `citation-review-ui.test.ts`:
- **Permission/eligibility:** `eligibleReviewers` includes only active, non-expired `reviewer`/`editor` members and excludes the owner and viewers/expired/inactive; empty roster → empty list (honest, no fabricated candidate).
- **No approval of unseen/uninspectable evidence:** `reviewSubmitGuard` blocks `approved` when `record` is null (masked) or `inspectionComplete` is false or `recordSha256` is null; allows `rejected`/`needs_changes` opinions where the contract does; blocks all while busy.
- **Masked record null safe:** the detail-mapper treats `record:null` as "withheld", never throws, exposes no field.
- **Stale hash → refresh not blind retry:** `isStaleConflict` maps `citation_review_stale`/`citation_review_conflict` to a refresh action; other errors map to the generic unavailable.
- **Selected version:** the reviewer pins the exact `recordSha256`; a changed detail hash invalidates a pending decision (guard recomputes against the freshly-read hash).
- **Empty state honest:** no findings → explicit empty, never fabricated live data.

Full component render, mobile/keyboard and runtime acceptance are **Codex verification before launch** — code is not production proof.

## Reviewer navigation blocker (documented; independent UI work continues)

The released P3 endpoints let a reviewer INSPECT and act on a finding **by its exact row id** and let the owner grant/revoke, but there is **no** authenticated "list the findings assigned to me" endpoint (the owner findings list is owner-only and must NOT be exposed to the team). So in this packet the reviewer opens a finding by an id the owner shares (deep-linkable), which is usable but not self-discoverable. The minimal, capability-scoped fix is a **separate additive migration** later: an RPC that returns ONLY the requesting reviewer's own active assignments (owner/project/findingRowId, never other findings, never the owner's full list), gated by the same live eligibility + assignment check. It is deferred here rather than shipped unverified; recorded as the next P4 step.

Findings authoring/creation, native import/parser (P5), panel binding, independent destination-content proof, an owner assignment-LIST / reviewer self-discovery inbox (see below), and the four-week manual pilot. No fabricated live data enters any client project; empty states are honest.

## First-review corrections — 21 September 2026

The first independent review (build/types PASS, focused 15/2 PASS) flagged that the pure guard tests do not prove UI wiring, plus concrete P1/P2 defects. All fixed in the same packet; the wiring decisions are now pure, unit-tested functions in `citation-review-ui.ts` (existing vitest infra, no new dependency), and the JSX consumes them.

- **P1 evidence rendering.** `ReviewerFinding` no longer shows `v.record` JSON as the primary surface. It renders the genuine cited evidence readably — each `v.evidence` item (answer: full captured text + citations + capture provenance + available/deleted; source: label/url/status + the SELECTED records' value/locator/status/validUntil + count; native: explicitly non-inspectable) and each dated `v.facts` entry (kind/value/validFrom–validUntil, or "unavailable" when deleted). Raw JSON is a collapsible `<details>` audit only. Owner detail likewise renders observation / hypothesis / recommendation / support (claim + status + reason) / assessed-accuracy resolution / current status / recorded date, with raw JSON collapsed. Approval stays gated on `inspectionComplete` **and** the material now being presented.
- **P1 deep link + navigation.** The route search now carries `owner` + `project` + `finding`; `reviewerLinkContext` validates the FULL context (owner/finding UUIDs, project slug), rejects partial/malformed links (no silent fallback), and reviewer requests use the **owner's** project from the link — a reviewer needs no project of their own or setup. A successful owner grant surfaces a copyable in-app scoped review link (`buildReviewerLink`, no external send). The previously-orphan route is now linked from the AI-visibility page. Query keys include actor/owner/project/finding.
- **P1 stale-decision binding.** The pending decision is bound to the inspected `recordSha256`: any hash change (new/edited version) or mask resets the decision + note (via a `currentSha` effect; `pendingDecisionInvalidated` is the tested pure form), so a refetch can never silently re-pin unseen data. Submit is disabled during fetch/refresh; a stale/conflict result refreshes and forces a fresh decision (never a blind re-pin). On a revoked/expired read the query error path renders no cached sensitive content and the decision/note clear.
- **P2 grant vs revoke + policy + honesty.** Grant candidates now mirror the LIVE approval policy (`readOwnerTeamPolicyFn`): `disabled`/none → nobody, `separate_reviewers` → reviewers only, `editors_can_approve` → reviewers + editors. Revoke targets are the FULL current roster (a departed/expired/inactive member can still be revoked) — separate from grant eligibility. Loading is distinct from empty; a roster/policy error is surfaced (not silent absence); a receipt-read error is surfaced (not "no reviews"); the finding's current status is refreshed after withdrawal; truncated receipt pages state the true total. The decision control has no default (no pre-selected "approved" implying inspection), selects/inputs carry accessible labels, and the note input is length-capped to the server's 2000. The owner query keys include the owner id. No automatic grants.
- **Tests.** `citation-review-ui.test.ts` covers policy-aware grant eligibility (disabled/null/separate/editors, excluding inactive/expired/owner), revoke targets (departed member still revocable), link validation (owner/reviewer/invalid + round-trip), the no-default/masked/uninspectable/busy submit guard, stale-conflict mapping, and version-pin invalidation.

## Second-review corrections — 26 September 2026 (recovery worktree `codex/milo-citation-review-recovery-20260926`, base `bab861c8`)

The old `/private/tmp` checkout was removed externally; Codex recovered the P4 files into this durable worktree. The independent follow-up review found five defects, all corrected here with Read/Edit/Write only (no Bash, commit, deploy, migration, provider call or dependency; the applied P3 SQL is untouched):

1. **Reviewer sees the record readably.** `FindingRecordView` is ONE shared presentation of the accepted `findingSchema` record (observation, hypothesis, recommendation status/target/suitability/passage, every support claim with status, cited URL, reason and the copied source passage the server returned, and the recorded accuracy judgements), used by the owner detail AND the assigned reviewer. It is rendered before the cited evidence/dated facts; the raw JSON is a collapsed `<details>` audit only. A `sourcePassagesWithheld` reviewer read shows an explicit notice. The reviewer only ever renders what the server returned for that caller.
2. **Stale/conflict recovery is explicit and tested as the real transition.** The reviewer form now runs on the pure `reviewerFormReducer` (consumed via `useReducer`, not a parallel helper): a `citation_review_stale`/`citation_review_conflict` submit result clears the pending decision and note unconditionally (a conflict can occur at the SAME record hash — a different decision/note already exists), sets the refresh notice and re-reads finding + receipts; a same-hash re-read keeps the clear; decision/note edits are ignored while a mutation is in flight. `canSubmitReview` is one predicate for the button and the handler, refusing a submit while the finding OR the receipts are being (re)fetched. The `staleRefreshed` copy now states both causes. Tests replay the event sequences (`citation-review-ui.test.ts`).
3. **Share link is a full URL.** `absoluteReviewerLink` prefixes the validated current application origin (`window.location.origin` at the browser boundary; an origin only — a base with a path/query/credentials/non-http scheme is refused) to the unchanged in-app path; with no valid origin it honestly returns the path. Route encoding/validation tests are unchanged and the full URL is round-tripped in a test.
4. **Own-receipt withdrawal after revocation.** Verified against the applied SQL: `remove_ai_citation_finding_review` permits a reviewer to withdraw their OWN receipt without a current assignment (only `reviewer_id = p_actor` plus account admission), while `read_ai_citation_finding_reviews` and `read_ai_citation_finding_for_review` require the assignment. The UI therefore keeps the reviewer's own active receipt withdrawable from the LAST receipt page React Query still holds when the reads now error, rendering no cached finding material (only the reviewer's own decision label and the withdraw control); a local withdrawn-id list keeps the control honest when the page cannot be refreshed, and a failed withdrawal is a distinct message instead of collapsing the whole surface to "unavailable". **True limitation:** a reviewer who opens the link fresh AFTER revocation has no receipt page (the list read fails closed), so the UI cannot learn the receipt id and offers nothing; the server would still permit the withdrawal by id. Closing that needs a small additive read (own-receipt-by-finding for the actor) — deferred, not claimed.
5. **Accuracy display uses the real contract.** The owner detail rendered `a.status` on the live `accuracy` entries, which have no such field (tsc failure). `AccuracyResolutionList` + `accuracyEntryDisplay` render `claimSpan`, the recorded `humanStatus` and the live `resolution` (labelled, nine states) plus the resolved capture date, typed against `CitationAccuracyResolution` so a wrong field is a compile error; a render regression asserts both values appear and no `undefined` is rendered.

**Tests added:** `src/components/CitationReviewPanel.test.ts` (static-markup render: readable record before JSON, withheld-passages notice, own-receipt withdrawal both while readable and after a revoked read with no cached finding material, nothing offered without a cached receipt page, withheld record, owner accuracy resolution) and new `citation-review-ui.test.ts` cases (absolute link, reducer recovery transitions, fetch-guarded submit, local withdrawal memory, accuracy display). i18n: 21 additive `citationReview.*` keys.

### Remount correction — 26 September 2026 (same worktree; `.coordination/p4-remount-correction-20260926.txt`)

Codex's real-browser review (`.coordination/p4-browser-review-20260926.md`: tsc, 39 tests, build PASS; many click gates PASS) proved a P1: a NEW mount of the reviewer surface after forbidden → withdraw rendered the PREVIOUS mount's React Query cache (full finding/evidence/facts/JSON and the decision control) while its own slow read was still in flight, because the sticky denial is mount-scoped but the query cache is client-scoped. Corrected:

- **Per-mount authorized read.** `ReviewerFinding` now scopes both query keys with a per-mount token (`newReviewerMountToken`, a counter — never tree-position derived — via `reviewerQueryKeys`) and sets `gcTime: 0` on both reads. A remount therefore starts with NO data (the earlier mount's entries are unobserved and dropped; no broad cache destruction, no server-contract change) and in-flight reads within one mount still deduplicate.
- **Exposure requires success, not presence.** `reviewerMaterialExposed({ viewIsSuccess, viewIsError, form })` gates `v`: material renders only after THIS mount's own read has succeeded, never on data presence (pending/in-flight/placeholder/cache), never on error, never while denied. A later background failure hides again (unavailable notice, own receipt only); a later background success is a new authorized read and exposes again. The submit/withdraw guards keep following live state.
- **Regressions.** `citation-review-ui.test.ts`: the gate (presence ≠ success; background failure; denied), unique tokens, key shape. `CitationReviewPanel.test.ts`: a mount whose reads hold data but have not succeeded renders "Loading…" only (no observation/claim/evidence/JSON/submit/withdraw); two renders get different mount tokens while both reads of one mount share theirs and keep the actor/owner/project/finding scope. Existing static tests were updated to carry `isSuccess`.
- **Harness.** New reviewer read mode "slow then revoked (4 s → error)", owner list modes (1 finding / true empty / error / slow) and owner detail error, with recipes 9–11 (remount while a slow read is in flight; remount into a delayed revocation with actions blocked throughout, then background recovery/failure; owner true-empty vs error vs loading, detail error). No production route for fixtures.
- **`initialReviewerForm` seam retained**, with the justification recorded on the prop: it only seeds the reducer state for DOM-less static renders; it cannot expose material (exposure needs this mount's successful read), cannot clear the live error/denied hide, and a seeded decision still passes the submit guards — it can only make the surface more restrictive.

- **Integration blocker: parent route onboarding guard.** Codex's independent check of the unchanged parent `src/routes/_authenticated/route.tsx` found `/app/citation-review` missing from `ONBOARDING_EXEMPT_PATHS`, so a hydrated ordinary reviewer with no (or an incomplete) own project was redirected into onboarding — contradicting the child route's promise. Narrow fix: the exempt list and the onboarding decision moved verbatim into the pure `src/lib/onboarding-guard.ts` (`ONBOARDING_EXEMPT_PATHS` now includes the exact path `/app/citation-review`; `onboardingRedirectNeeded({ pathname, projects, activeProjectId })`), and the layout calls it. Authentication (`/auth` redirect with the preserved `redirect` target), hydration, the failed-hydration screen, the role-loaded/owner bypass and the effect ordering are untouched. The exemption grants no access: the route still validates the link and the server still re-checks the finding-scoped assignment. Regression `src/lib/onboarding-guard.test.ts`: zero/incomplete own projects on the review path → no redirect; the same users elsewhere → redirect; set-up active/first project → none; only the exact path is exempt (sibling/prefixed paths still onboard); all previously exempt paths kept. The component harness mounts below the parent and cannot show this; the real route journey stays with Codex.
