# Private MCP image import — 9 September 2026

Base: PR #102 merge `1699bc8b384726cd501da7492b4212b499f06f77`. Implemented and locally verified; review, receipt migration and release pending. This is R08/R18 image authoring, not a claim that every external AI client has passed acceptance.

`add_content_image` accepts assistant-supplied JPEG/PNG/WebP files up to 5MiB, as canonical base64 with a stable requestId, explicit owned project/draft, concept and alt. It requires OAuth `milo.content.write`, a named client, the existing write flag and a confirmed persistent write quota. Legacy tokens and read-only grants cannot use it. Unknown fields, URLs, data URLs, permissive base64 variants, oversized bytes, injected paths/status and non-raster signatures are refused before storage. Validation reuses the existing signature/size gate; this does not claim full raster decoding or malware scanning.

A server-preserved project receipt binds client/request/target, exact byte and metadata digests and a minted image/path identity before storage. Storage is private, correctly typed and never upserted. Identical stored bytes can be recovered after a lost upload response. Both workspace callbacks check current ownership/draft/publication state. The final callback appends one proposed inline image, preserves concurrent edits and invalidates stale assessments. Replay does not restore removed images or reverse later owner edits/approval. It reports current recorded image status, not newly performed approval. The image uses the existing owner approval/promotion workflow. No AI provider call, generation-allowance claim, scheduling, publication, arbitrary remote fetch or email.

Ordinary MCP bodies and all batches retain the 200,000-byte limit. Only one image call from an OAuth content writer may use the 7,100,000-byte envelope needed for a 5MiB file. Actual bytes, chunks and ten-second read deadlines remain enforced. At most two large bodies may be in progress through dispatch in one server process, retained until all tracked physical storage/workspace operations settle, including after a timed-out response; this is a memory bound, not a cross-host rate quota. Storage/workspace waits are ten seconds per operation. Late/uncertain writes are not declared rolled back; retry only identical data with the same requestId. No provider attempt is repeated by this mechanism.

Receipt history is bounded at 200 imports per project and existing images at 30 per target draft. These are internal safety limits, not new commercial packages. Migration `20260909140000_preserve_mcp_image_receipts.sql` extends the existing preservation trigger to retain `mcpImageRequests` through stale/ordinary browser saves. It creates no records or images. Production preflight found zero existing image receipts, a private staging bucket and its existing 5,242,880-byte storage limit. No mutation performed in that check.

Verification: Final full suite: 2,159 tests / 149 files passed, including 77 new cases covering strict bytes/input validation, cross-target/path binding, replay/concurrent calls, owner removal/edits, approval during upload, quota/scope/flag denial, audit privacy, identical-file recovery, late uploads, larger-body routing and memory admission. The editor now refreshes private thumbnails on mount, before expiry, after a stale-image error and when refocused; URLs stay in view state and never change content or approvals. A scoped authenticated server read signs only the caller-owned path. Stable public URLs take precedence. Live external-client transfer, visual approval and CMS destination fidelity remain acceptance work. Browser automation remains blocked by its administrator-policy check; no workaround used. OpenAI reauthentication is still needed for the separate paid benchmark; no OpenAI connection or cost is needed for this import path.

The immutable upload behavior follows the installed Supabase storage client and [Supabase's standard-upload concurrency contract](https://supabase.com/docs/guides/storage/uploads/standard-uploads): first upload at a path wins unless explicitly upserted. The implementation independently checks stored bytes before recovery and never enables upsert.

## Review corrections before release

- Attachment time is captured after storage. Shared draft writes preserve a later current timestamp (including sub-millisecond precision), so the actual newer-wins database trigger cannot silently drop an image while the project receipt reports attached. A PGlite regression applies the real trigger and verifies that both content and receipt persist. The same guard protects the existing controlled benchmark's image attachment.
- Request admission now tracks the physical promises as well as the caller lifetime. A timeout does not release the slot while upload/download/workspace I/O still owns buffers. If both slots remain unresolved, further image work is refused until settlement or process recovery; ordinary reads remain available. Route/core tests cover the late-settlement boundary.
- Private image preview renewal is included in this same packet, with 19 authenticated-read and lifecycle tests. No signed URL cache is shared across mounted views/login sessions, no URL is returned in MCP audit/results and no preview refresh performs a mutation. Browser visual acceptance remains unavailable.
