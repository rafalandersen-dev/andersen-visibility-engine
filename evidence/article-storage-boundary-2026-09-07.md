# Article image storage boundary

Read-only production inspection found both article buckets with null file_size_limit and allowed_mime_types. The private bucket is private and the public bucket is public. Each contains one object; maximum recorded size367112 bytes. Existing authenticated policies permit direct insertion and deletion of owner-prefixed public objects, bypassing the application's promotion/validation path.

Migration20260907220000 applies the existing5MiB JPEG/PNG/WebP contract to both bucket upload configurations, preserving any stricter compatible size/MIME setting and refusing an incompatible configuration instead of widening it. It adds restrictive INSERT/UPDATE/DELETE policies for anon/authenticated on the public article bucket, including moves into that bucket. Public reads, private/unrelated bucket policies and service-role writes remain as before. Existing objects are not edited or deleted. All source public promotion/removal callers use image-storage.functions.ts and the service role; no direct browser Storage write to these buckets was found.

Validation: 1,519 tests/116 files, TypeScript/build pass on main #79. Seven new real SQL-engine cases exercise direct anon/authenticated writes despite an intentionally broad permissive policy, public reads, moves into public, private/unrelated objects, service-role promotion/removal, repeatability, stricter limits and incompatible MIME refusal. Exact migration also passed connected PostgreSQL configuration/policy assertions in a completely rolled-back transaction. Follow-up shows original null settings and both existing objects retained. Migration has not yet been permanently applied/registered.

This is storage admission/RLS hardening. It does not establish a full raster decoder, signed external-upload flow, URL ingestion, public-upload HTTP acceptance or protected UI acceptance. Existing byte validation is a size/signature check. Do not claim arbitrary remote URL ingestion is ready; it needs a separately verified egress boundary. Supabase signed uploads remain a future bounded intent/confirm packet.
