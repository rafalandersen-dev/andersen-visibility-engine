P1 imports `native-ai-report.ts` with a **single, additive `export` modifier** on the existing `nativePeriodSchema` (so the artifact metadata reuses its exact real-calendar/ordered validation rather than a weaker local copy); no logic in that file changes, so it does not overlap that file's pending review. The workflow reuses the answer-evidence stack verbatim:

- **Server permission:** `public.assert_knowledge_project(p_user,p_project[,write])` gates every RPC and takes the `FOR UPDATE` account lock on writes.
- **Server libs/fns:** `answer-evidence.server.ts` (`call()` 10 s-timeout RPC wrapper) and `answer-evidence.functions.ts` (`createServerFn`+`requireSupabaseAuth`, `context.userId !== data.expectedOwnerId → evidence_owner_changed`).
- **UI/export:** `AnswerEvidencePanel.tsx` (React Query read, `mutate()` guard, client `download()` JSON export); `analyzeAnswer`/`evidenceCohorts` in `answer-evidence.ts`; `escapeForSpreadsheet` in `native-ai-report.ts` (reserved for a real spreadsheet/CSV path, never applied to canonical JSON).

New tables are added only where §8 forbids reuse.

## 2. Minimum typed extension; immutable version / correction / reference binding

Extend, don't reinvent (§8). Logical stores, each mapped to the existing invariants — added over the sequenced packets, no five-table up-front mandate:

1. **Native raw artifact (P1, this packet)** → new `ai_native_report_artifacts`: owner-supplied opaque export **bytes** with a server-derived `sha256`, bounded, private and owner/project-scoped. It carries owner-declared scope metadata and an explicit `pending_parser`/`unsupported` status; it holds **no** parsed rows/cells/values and yields **no** metrics, presence, comparability or verified claims. Same-scope reimports version via `nativeArtifactScopeKey` + `sha256`, linked by `supersedes_id`.
2. **Panel/session protocol (P2)** → new immutable `ai_citation_panels` (one row per `(panelId,version)`), validated by `panelProtocolSchema`; questions reference existing `ai_visibility_prompts (id, revision)`.
3. **Capture context (P2)** → embedded in the existing `ai_answer_evidence.document` under a `captureContext` key, reusing its hash/dedupe/cap/supersede path (no second capture table).
4. **Dated owner-confirmed business facts (P2/P3)** → resolved from **actual trusted records**, with the server deriving classification and reviewer identity; a source-helper reference binding does **not** authenticate a client's claim.
5. **Finding / improvement (P3)** → new `ai_citation_findings`, `ai_citation_improvements`, validated by `findingSchema`/`improvementSchema`; task references reuse the existing Plan model.

Reference binding is enforced by the helpers end-to-end: capture→answer→prompt(id+rev) via `slotOutcome`; finding→`evidence[]` ids; improvement→`findingIds`+`baselineCaptureIds`+`taskId`; retest→`comparablePairs`. Immutability = append-only versions plus supersede chains; corrections never rewrite originals.

## 3. Auth, server-derived facts, raw-artifact storage, deletion/retention

Every endpoint copies `answer-evidence.functions.ts`: `requireSupabaseAuth` → `context.userId`, `expectedOwnerId` equality, then `assert_knowledge_project(user,project,write?)`. **Server-derived, never imported:** the artifact SHA (over decoded bytes), stage id, created time, actor, status, byte length, the canonical scope key (derived inside the DB from validated metadata, not supplied by any caller) and supersession — and later reviewer identity/classification/parser version. A metadata body is accepted only as a strict allowlist of the declared keys, so any parsed/server-only field or arbitrary extra key is refused at both the strict Zod boundary and the DB.

**Raw artifact (decided):** store bounded raw bytes with a **server-computed SHA256**, private and owner/project-scoped, with deletion and JSON export included. Conservative cap **20 artifacts/project (including versions and corrections) AND 40 MiB total raw bytes/project**, no eviction and no cap raise; at the 2 MiB per-artifact bound (`MAX_NATIVE_REPORT_BYTES`) these two coincide (20×2 MiB). This provisional engineering bound supports four weeks of two streams plus corrections and needs no new subscription or spend. Bytes are opaque: no execution, automatic fetch, archive extraction or file-format assumption; the encoded body is length-bounded (≤ base64 of 2 MiB), strict-base64-regex + multiple-of-four checked **before** decode, then required to survive a **canonical round-trip** after decode (rejecting whitespace, misplaced padding, non-alphabet characters and non-canonical trailing-bit encodings), with the actual byte bound re-checked; no unbounded body or JSON parse of the bytes. These base64 guards hold at the DB boundary, not only in the JS validator.

**Idempotency (scope-correct, DB-derived — no caller key):** the save RPC **takes no scope-key parameter**. It strictly validates the declared metadata (a ten-key allowlist with strict sub-object shapes, enums, real ordered Gregorian dates and the GSC timezone, alpha-3/exposed market rule, bounded filters, offset-ISO `capturedAt`) and derives the canonical scope key itself as `sha256` over the ordered canonicalized fields — source, normalized property (scheme+host lowercased, path/query case-significant), reportKind, dimension, aggregation, period start/end, timezone, uppercased country, exposed, and filters embedded as a jsonb object so **filter key order is irrelevant**. `UNIQUE(user,project,scope_key,sha256)` makes same-bytes+same-scope idempotent; the same bytes under a different source/property/period/filters/aggregation form **distinct lineages** that never collapse or supersede. Records are append-only; because identity is derived inside the DB from validated metadata, a forged or unrelated scope key cannot enter. The client `nativeArtifactScopeKey` (now a bare delegate to `nativeSnapshotScopeKey`, which already folds in `aggregation`) is a client-visible **predictor** used only in tests, and the same-scope reimport supersedes the current head under `UNIQUE(user,project,supersedes_id)`.

**Export / retrieval / deletion:** the **list** RPC returns bounded metadata **only** (never 20×2 MiB of bytes); **single** retrieval is explicit + authenticated and returns the exact bytes verbatim as base64 (JSON export retains bytes/text/metadata unchanged; formula-escaping is only ever for a real spreadsheet/CSV format, never rewriting canonical JSON evidence). No public URLs or service keys. Explicit deletion removes **only the selected artifact's** raw bytes and frees **only its** quota: the self-FK is `NO ACTION` (not `CASCADE`), and `remove_*` atomically unlinks any direct successor (`supersedes_id → NULL`) before deleting, so removing a predecessor never destroys a distinct later version the owner kept — the successor survives as a lineage root and a later same-scope reimport supersedes the surviving head. The deleted predecessor's id/metadata/bytes are not retained, but the orphaned successor records a **server-derived `predecessor_deleted=true` marker** (returned/validated through save/list/get, `false` for a genuine first version, never caller-writable), so the history gap is visible in the data itself — a partial chain is detectable and is never presented as complete lineage proof. Project deletion CASCADEs all artifacts via the `workspace_entities` FK. P3 formalizes atomic cross-entity deletion so a removal invalidates every dependent inspectable claim.

## 4. UI flow (extends existing AI area, Plan, Reports — no new "Authority" product)

`draft panel → owner lock → existing manual intake + capture context → human findings → existing Plan/Studio approved change → destination receipt → qualified re-test / report.` Three peer evidence tabs (Google native, Bing native, manual) with citation/source and recommendation/accuracy findings as equals (§10). Reuse `AnswerEvidencePanel` for capture intake; add panel-lock, findings review, improvement/verification and re-test/proof views. Render all answer/source text as safe text; no HTML/Markdown/formula/remote-image execution (§9). States surfaced: not configured, unavailable, `unknown_export_zero`, preliminary/partial, unreviewed, reviewed, no-presence, missed/failed/truncated, protocol-change, incomparable-pair, capacity-reached, superseded, evidence-deleted, **and staged/`pending_parser`/`unsupported`** (a staged artifact shows as awaiting-parser, never as numeric data). No connect-API / autoprobe / add-provider buttons.

## 5. Native upload / preflight boundary (P1 stages; parser awaits genuine columns)

P1 storage/server proceeds now as **raw-artifact staging**; the **column mapping stays gated** until a real owner export exists (§3.3). No speculative parser, no CSV schema, no API/OAuth adapter. The stage endpoint accepts the artifact bytes + owner-declared metadata (source, property, reportKind, dimension, aggregation, period, timezone, filters, market scope, capturedAt, filename), stores bytes+server SHA under `pending_parser`, runs the byte/base64-bound validation and a capacity preflight against the remaining 20-artifact/40-MiB budget, and records availability as **staged/unknown** — never numeric zero, never fabricated cells. An `unsupported` status is set later by a reviewed action, never by claiming the raw bytes parse.

## 6. Concrete tests (per packet; deterministic, offline; synthetic fixtures never enter a client project as live results)

## 9. Resolved product decision (retention)

The earlier open choice — whether to store native raw bytes server-side and the per-project cap — is **decided under the working agreement**: store bounded raw bytes with a server SHA, deletable via `remove_*`, at a conservative provisional bound of 20 artifacts / 40 MiB per project (no eviction, no raise, no new spend). Rationale: it enables genuine later re-review, export and a real parser (P5) from stored evidence, while the bound and private owner/project scope keep the storage and deletion surface small. Capture-context embedding in `ai_answer_evidence.document` remains the P2 default and P1/P3 do not depend on it.

## Limitation

P1 code + migration file + tests + docs are written, with six Codex-review/probe corrections applied (real-date enforcement, non-destructive deletion, DB-derived scope with no caller key, strict base64 at the DB, strict null/type handling for the required enums against SQL three-valued logic, and a server-derived `predecessor_deleted` history marker — see `evidence/citation-artifact-staging-2026-09-19.md`); **no migration was applied**, no endpoint deployed, and the two corrections completed in this worktree and their new regressions were **not run here** (the sandbox `posix_spawn` E2BIG blocker recorded in `evidence/citation-review-2026-09-19.md` persists — Codex runs the prepared tests under the recorded exception). No DB, network, provider, export, collection or dependency change occurred. The PGlite harness is a single connection, so it verifies logical guards (unique supersession, transactional caps under the account `FOR UPDATE` lock) and **claims no true concurrency**; the deleted-predecessor history gap is now marked in the data (`predecessor_deleted`) but the marker retains no deleted bytes/metadata and is not a claim of complete lineage proof. Genuine native exports, the owner-approved panel and the four-week manual pilot remain outstanding real-acceptance gates.

Assessed finding accuracy is wired to the **immutable fact ROW id + kind + the SAVED answer-evidence capture time** via narrow additive `factRowId`/`factVersion`/`captureEvidenceId` on `accuracySchema` (pure framework unchanged): an assessed entry pins the exact fact row UUID (a deleted-then-recreated fact reuses the numeric version but not the row, so the old assessment stays `fact_missing`) and anchors the comparison to one of the finding's own answer references, whose capture instant is resolved server-side from the actual saved contract `document.input.capturedAt` (never owner free-text, and a fake top-level date does not resolve; native-only/unbound → `capture_unresolved`). Resolver casts are staged behind guards, malformed audit pins are normalized to null, and read-back audit ids use a read-only canonical (hex) type so a legacy non-RFC id round-trips instead of failing `.uuid()` (write path stays strict); the finding detail is a discriminated union on a server-derived `recordValid` — a well-formed finding returns the EXACT strict `findingSchema` record (`recordValid:true`) and a malformed one returns its raw record as a bounded, JSON-serializable value (`recordValid:false`) that is depth-capped and byte-capped to the finding storage budget and is a concrete transport-safe type (never `unknown`, so it satisfies the server-function serialization contract) — so a legacy/malformed finding stays inspectable and deletable rather than crashing the detail, and a pathologically deep/oversized record is refused (fails closed) instead of returned. Fact validity is one consistent MICROSECOND precision across input/columns/export/digest with sub-microsecond input refused (no silent truncation); the digest hashes the normalized meaning (equivalent `Z`/`+00:00` restage is not a fake correction; `…100100Z` vs `…100900Z` stay distinct).
