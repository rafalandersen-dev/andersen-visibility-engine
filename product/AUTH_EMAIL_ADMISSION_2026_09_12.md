# Branded authentication email admission

Prepared after 13ee5a8 on codex/milo-report-branding-authority-20260912. Unreleased; overall 60% / implementation 75%, paid NO-GO and existing release/provider/account boundaries persist. Addresses the application-level request-admission portion of R23/R24; not full authentication abuse or live acceptance.

Current signup and password-reset handlers used administrative link generation and branded email delivery without their own shared request limit. Added admission after input/configuration checks and before generateLink. Both handlers use the same recipient counters, so changing between signup and reset does not create another allowance.

Initial bounded private-beta policy: one request per normalized recipient per fixed UTC minute, six per fixed UTC hour, and 120 per service per fixed UTC hour. Attempts consume counters, including attempts that later fail; these are not billable usage or delivered-email counts. Recipient rules are checked first to avoid repeated requests for one recipient consuming the service counter. The global cap can still be exhausted by distributed abuse and therefore can deny legitimate requests; thresholds require operational review before launch. Fixed-window boundaries allow adjacent-window bursts. This does not implement IP/device/bot protection or replace native auth controls.

Reuses the existing service-role-only bump_rate_limit RPC from migration 20260708190000_oauth_rate_limits.sql, whose single insert/on-conflict update increments atomically across instances. Existing cleanup removes windows older than 24 hours; all added windows are at most one hour. No new migration, grant or cleanup job is required. RPC response errors, rejections, missing/malformed counts and unavailable key material stop the operation. Returned diagnostics are fixed generic messages.

Recipient and global counter keys are HMAC-SHA256 values keyed by the existing server service-role secret with bucket-specific input. Raw addresses/secrets are not stored in this counter table. Normalization is trim/lowercase; mailbox aliases remain separate. Rotating the server key resets the effective counter identity. No client IP/header trust or new credential is introduced.

Verification covers normalized/hash-only keys, shared service identity, invalid/error responses, inclusive limits, early stopping and refusal before administrative link/render/token/send calls in both real handlers. Tests use mocked RPC/provider boundaries; they do not prove production database installation, distributed live concurrency, mail delivery, rate-limit usability or bot resistance. Confirmation resend and native delivery configuration remain unfinished.

Validation passed: 102 tests across three files, full TypeScript, production build and zero lint for the new limiter and changed tests. The existing handler retains its three previously recorded typing findings. Logs /tmp/milo-auth-admission-{tests,types,lint,build}.log. No live counter mutation, authentication, email, credential operation or deployment was performed.
