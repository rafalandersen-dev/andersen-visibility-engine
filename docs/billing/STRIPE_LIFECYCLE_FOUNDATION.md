# Stripe subscription lifecycle — dormant foundation (28 October 2026)

**Status: prepared code with local tests only. Public paid activation stays HELD, and nothing here is production acceptance.** This packet creates no Stripe object, consumes no credential, touches no production data and activates no billing. Live checkout _and_ the live billing portal are refused by code constants, not by configuration. Manual beta/comped access, legacy Paddle subscriber management and the existing isolated sandbox adapter are unchanged. The USD 50/month global AI ceiling and the manual-budget prerequisite for free accounts are untouched.

There is **no configured isolated sandbox**: no company-owned Stripe test environment, account id, restricted key, price or webhook secret exists in the authorized scope, so no end-to-end path has ever run. Local unit tests and a PGlite migration harness prove the _decision logic and the SQL contract_; they prove nothing about Stripe's own behaviour.

### Trust boundary

- **No direct table writes from TypeScript.** Every database _mutation_ on this path is a `SECURITY DEFINER` function granted to `service_role` only, with RLS enabled and no policies. Ownership, lease fencing, receipt state and the entitlement predicate cannot be bypassed from application code. Legacy `claimWebhookEvent` / `writeEntitlement` are not used by this path. This foundation reads no table directly either; the commercial stage layered on top adds exactly two **read-only**, service-only, fully scoped `SELECT`s of its own (see the status correction at the end of this document and limitation 13 of `STRIPE_COMMERCIAL_OPERATIONS.md`), which write nothing and return nothing to a caller. The earlier unqualified phrase "no TypeScript table access" is corrected to that, so the boundary is stated as what it actually is: no direct writes, plus narrowly scoped service reads.
- **Payload is not evidence.** A webhook body is used only to verify the signature, detect the mode and retain `(event id, type, object id)`. Plan, status, period, customer, ownership and the originating checkout request are all taken from a fresh authoritative read. `event.created` decides nothing, and **no metadata — ours or anyone's — ever establishes ownership**.
- **Ownership is server-side only.** A Stripe customer is linked to a user exclusively by `stripe_upsert_customer`, called during server-resolved checkout creation. The webhook path never calls it.
- **Mode isolation is structural.** The entitlement block in `stripe_apply_subscription_projection` is wrapped in `IF p_mode='live'`. Test-mode activity of any kind reads and writes no entitlement row at all.
- **Account identity is verified before every provider mutation.** A restricted-key prefix proves live/test, not _which_ account, so `GET /v1/account` is read and compared with the mode-specific configured id before customer creation, session creation, portal creation and before any session is reused. An unverifiable account mutates nothing.
- **Uncertainty neither grants nor revokes.** Unreadable, incomplete, ambiguous or foreign evidence leaves the receipt retryable and answers the provider with a retryable failure. An unknown result is never reported as success.

### The grant is re-derived in SQL (the caller is not trusted)

`p_grants` is a request, not a decision. `stripe_apply_subscription_projection` independently requires **all** of: `p_mode='live'`; a sellable plan (`stripe_sellable_plan`); status `active` or `trialing`; `p_invoice_paid`; and a non-null, **finite**, future `p_period_end` bounded to five years, compared against the **database wall clock** (`clock_timestamp()`).

A claimed grant that fails this predicate is refused outright — outcome `grant_unverified`, receipt left `uncertain`, **nothing written at all** — rather than silently downgraded, because downgrading a forged "active" would be an unasked-for revoke. The adversarial SQL tests cover a forged `true` next to a canceled, unpaid, period-less, elapsed, infinite, implausibly distant, unsellable-plan and unrecognised-status projection, and show it cannot grant, **restore** a revoked entitlement or **extend** an existing period, in live or test mode.

Revokes are equally narrow: only `stripe_revocable_status` values (`past_due`, `unpaid`, `canceled`/`cancelled`, `incomplete`, `incomplete_expired`, `paused`) may change an entitlement, only where `provider='stripe'` **and** `provider_subscription_id` equals the exact subscription being processed, and never for `manualBeta`/`manualComped`. A status this code does not recognise changes no entitlement (`revoke_not_applicable`), and a legacy provider row that currently grants paid access is preserved (Stripe may only take over a non-granting row; note the live default for `entitlements.provider` is `paddle`). Entitlement writes are single conditional statements, so a concurrent manual override wins or loses atomically.

### Evidence, not booleans

Payment evidence has **three** values, and they are not interchangeable:

- `paid` — `status === 'paid'`, matching `livemode`, matching customer, `parent.type === 'subscription_details'` with the right subscription, `amount_remaining === 0` when present, and a real `status_transitions.paid_at`;
- `unpaid` — a genuinely non-paying invoice status (`draft`, `open`, `void`, `uncollectible`) or an outstanding amount on a `paid` invoice;
- `unknown` — absent, unexpanded, unreadable, foreign (other customer/subscription/mode), malformed or an unrecognised status.

The removed `invoice.paid` boolean is never consulted, and a legacy top-level `invoice.subscription` is ignored. `unknown` is missing evidence, so it can never justify a revoke. There is exactly **one** payment rule (`invoicePaymentEvidence`) — the earlier separate `invoicePaymentProof` helper is gone, so "paid" cannot come to mean two different things in two places — and `grantsPaidAccess` takes its result, never an assumption that "not unpaid" is good enough.

Subscription reads are the same shape. Identity is checked first and strictly (object discriminator, id shape, `livemode`, expected customer, recognised status, boolean cancel flag); failure means the object cannot be interpreted and the caller stays uncertain — it is never downgraded to "no subscription". Unresolvable items (unknown price, missing or elapsed period, unreadable or paginated item list) are returned as _item evidence_, so an active subscription with missing evidence stays retryable **with its entitlement intact**.

Lists are validated for completeness: `object === 'list'`, `has_more === false` and an actual `data` array. **A missing `data` is not an empty list**, and a full page is treated as incomplete.

### Current-subscription resolution (serialized)

Processing holds a fenced per-account/per-mode lease, so deliveries are serialized. For each receipt the server verifies the key-owning account, re-reads the referenced object (checking that the object returned is the one asked for, of the expected kind and mode), resolves ownership from the server mapping, then lists that customer's subscriptions (`status=all`).

- Two grant-eligible subscriptions → **uncertain**; nothing written.
- One grant-eligible subscription with complete evidence → applied; the grant itself is then re-derived in SQL.
- One grant-eligible subscription with incomplete evidence → **uncertain** (no grant, no revoke).
- A stored subscription **absent** from a complete read → **uncertain**. Absence is never proof of cancellation or replacement.
- A replacement applies only when the stored subscription is shown **terminal** (`canceled`/`incomplete_expired`) in the _same_ complete read, is named in `p_replaces`, and the observation is strictly newer than the stored one.
- The stored subscription in an explicit non-granting state → a non-granting projection for that exact subscription (the revoke path), using the stored plan when its items no longer resolve.
- No stored subscription and nothing grant-eligible → acknowledged, nothing written.

Staleness is guarded by the **observation time of the authoritative read**, taken from a fresh clock read _after_ the reads complete, never from a request or batch start time.

### Subscription-existence versus entitlement-grant statuses

Two different questions, two different sets:

- **Grant** (`ENTITLEMENT_GRANT_STATUSES`): `active`, `trialing`.
- **Over, so a new checkout is allowed** (`TERMINAL_STRIPE_STATUSES`): `canceled`, `incomplete_expired` — and nothing else. `incomplete`, `past_due`, `unpaid`, `paused`, any unrecognised status, any unreadable subscription object and any incomplete list all **block** a second checkout, because a duplicate paid subscription is not recoverable by retrying.

### Durable recovery (real, bounded, per receipt, service-only)

`stripe_record_webhook_receipt` distinguishes `recorded`, `retry` (received but not completed — a duplicate delivery after a crash or lost acknowledgment is processed again), `completed` and `exhausted` (past the attempt limit; kept for an operator, never discarded). A redelivery with a different body fingerprint is a conflict.

`replayPendingStripeReceipts({ mode, limit })` claims **one** receipt at a time (`stripe_claim_replay_receipt`, `FOR UPDATE SKIP LOCKED`), each under its **own fresh fenced lease** and its **own clock read**, re-fetches the current object from the retained identifiers and runs exactly the same reconciliation as a live delivery. One claim equals one real processing attempt: a batch claim would charge attempts to receipts that a lease expiry never processed, and 25 receipts cannot share one short lease. Only metadata is persisted — no raw event body, no payment data.

**Each receipt gets at most one turn per invocation.** The claim takes a validated, bounded `p_exclude text[]` — the event ids this invocation has already processed — so the oldest retryable receipt is no longer re-picked every pass. Without it one transient provider outage spent a whole run, and a whole slice of the bounded attempt budget, on the same receipt while newer pending rows never got a turn (reproduced: `evt_old` claimed four passes running, attempts 1→4, `evt_new` never claimed). Excluded rows are not read, not locked and not charged an attempt; only the row actually claimed is. The exclusion lives **only in that call**: a later invocation passes an empty set, so an uncertain receipt is simply retried then, with its own fresh lease and clock — nothing is acknowledged, downgraded or discarded, and there is no inner retry loop. The set is validated rather than trusted (one dimension, at most `stripe_replay_exclusion_limit()` = 25 entries, no NULL or blank id, no duplicates; an invalid set raises `stripe_replay_exclusion_invalid` and claims nothing), and matching stays scoped to the one account and mode. A claimed row whose id is unusable cannot be excluded, so the invocation stops after recording that attempt instead of claiming it again.

Lease safety:

- liveness is compared with `clock_timestamp()` — the wall clock **after** the row lock was granted — not with transaction-start `now()`, so a holder whose lease expired while waiting for the lock loses;
- `stripe_require_lease` guards the projection, the receipt transitions and the webhook-side request expiry, so an expired holder cannot terminally acknowledge a receipt a new worker owns;
- `stripe_renew_account_lease` extends only a lease still owned at the same fence and still live — it cannot steal a live lease, resurrect a dead one or advance the fence — and reconciliation renews immediately before the write, so a lease lost during the reads stops the write (and writes no acknowledgment either).

Completion, projection, entitlement and the originating checkout-request settlement are **one transaction**. The projection refuses to write unless the lease still names this holder at this fence and is live, and a receipt for this exact event/account/mode exists and is still retryable.

### Checkout and portal

Callers send only `{ requestId, planId, seatQuantity? }` — a strict validator rejects an injected price, customer, owner, account or mode. The owner comes from the authenticated session; the account, mode, prices and return URLs are server-resolved.

- **Live checkout and the live portal are refused in code** (`liveModeAllowed()` returns `false`; both service entrypoints refuse `mode === "live"`) before any provider or database access.
- Test mode requires the caller's UUID in `MILO_STRIPE_LIFECYCLE_SANDBOX_OWNERS`, which is **empty by default**.
- Request idempotency is persistent and scoped to owner/account/mode/kind **and the selected parameters**. A partial unique index allows at most one non-terminal request per owner/account/mode/kind, so another `requestId` or a re-navigation cannot start a second Checkout.
- **Aged ambiguous attempts are FENCED, not failed.** At or past Stripe's 24h idempotency retention — the boundary itself counts as outside the window — or with an unreadable creation time, the request moves to the non-terminal `fenced` state: the unique slot stays held, so no new `requestId` can create a second subscription. Age alone never releases a slot and never fails a request.
- **The retention deadline is re-read immediately before every duplicable mutation.** The deadline is derived from the request's **immutable** stored creation time, so no amount of waiting restarts it, and it is re-evaluated against a **fresh** clock directly before the customer `POST` (when no mapping exists) and before the Checkout `POST`. A single pre-await check was not enough: the awaited steps in between — account verification, the customer mapping read and the acknowledgment of a created customer, the authoritative subscription list — can each take long enough for an attempt that began inside the window to cross the boundary, where a repeated idempotency key is a **new** attempt that could create a second session. On a crossed deadline, or a clock that cannot be read, the attempt is fenced (non-terminal, slot held) and **zero** new provider mutations are dispatched. A mutation that already went out is left exactly as unknown as it was — a created customer stays created and mapped, and nothing assumes a cancellation. The payload and the idempotency key are unchanged, so a retry inside the window still resumes the same request.
- **Recovery is authoritative.** A retry of a fenced request lists the caller's own Checkout Sessions and either adopts the session that really exists (identity re-checked) or — only when a _complete_ list proves no session with that `client_reference_id` exists — settles the request `failed`. An incomplete, unreadable, ambiguous or unavailable list leaves it fenced, as does a caller with no mapped customer.
- **A `complete` session is never marked expired.** Only an authoritative `expired` settles `expired`; a `complete` session stays blocked until the projection shows the subscription it names mapped to this owner, at which point the request is settled `completed` (so it cannot block forever). An unrecognised status is uncertainty.
- A successful checkout webhook settles **only** the exact mapped request: the session's own `client_reference_id`, cross-checked against the server-resolved owner, the account, the mode, `kind='checkout'`, the exact session id and the subscription actually being applied — committed in the same transaction as the projection. An unrelated event cannot release another request's slot.
- A customer mapping read error fails uncertain; it never creates a second customer. Customer creation uses a persistent per-account/mode/user idempotency key, and the created object's `object`, id shape and `livemode` are re-checked.
- Returned sessions are validated: `cs_<mode>_…` id, `livemode`, our customer, our request id, and an `https://checkout.stripe.com` URL with no port or credentials. A session that came back with an unusable URL or an unexpected status is still **recorded** (it exists at the provider) and refused to the caller.
- The portal URL must be on **exactly** `billing.stripe.com` with no port, username or password, and the session must be `billing_portal.session`, in this mode, for this customer. A suffix test such as `endsWith('stripe.com')` would have accepted `billing.stripe.com.evil.test`; it is gone.
- An ambiguous **portal** attempt keeps its retry safety, and the reviewer accepted that boundary: creating a second short-lived link to the caller's **own** mapped customer is not a financial mutation and cannot duplicate a charge, so age never fences or fails a portal request — at worst a retry mints another link for the same owner. The identity checks are unchanged and still mandatory: the caller's own pre-existing mapping only (no customer is ever created here), the key-owning account verified before the mutation, and the returned session validated as `billing_portal.session`, in this mode, for this customer, on exactly `billing.stripe.com`.
- No `payment_method_types`, no `automatic_tax`. `integration_identifier` is built from a stored eight-LETTER configured suffix (a UUID fragment is rejected).
- Returning from a successful checkout grants nothing; only a reconciled projection can.

### Seat reads

`stripe_purchased_working_seats(user)` returns extra purchased working seats only from the **live** projection, and only when the entitlement owns that exact subscription, is `active` with provider `stripe` and an agreeing plan, the latest invoice is paid and both periods are still current. Everything else — test mode, manual/comped, free, legacy provider, lapsed or missing period, unpaid invoice, disagreeing plan — is 0.

**Both periods are required to be present, finite and in the future, and the requirement is now written identically on both rows.** The earlier clause was `e.current_period_end IS NULL OR e.current_period_end > now()`, which paid out a period-less entitlement: reproduced on PGlite with a valid live `pro` subscription, a paid invoice, four extra seats and an active Stripe entitlement whose period was `NULL`, the read returned **4**. An absent, `infinity`/`-infinity` or elapsed period on either row — the projection or the entitlement that owns it — is now 0, because a malformed period must never become an unlimited grant. The exact mapped ownership (live mode, `provider='stripe'`, `status='active'`, agreeing plan, matching `provider_subscription_id`) is still required on top of both periods; nothing about that was relaxed. The grant predicate in `stripe_apply_subscription_projection` already refuses to **write** such a row, so the only way to hold one is a manual or legacy edit — which must not pay out either.

In `project-team-seats.server.ts` both public reads (`readTeamSeatAllowance`, `readTeamSeats`) now **cap `freePreview` at its own bundle** and do not call the extras read at all in that state. `resolveEntitledPlan` fails closed to `freePreview`, so `freePreview` means "free account **or** a failed entitlement read", and an entitlement outage must never widen an allowance. For a paid plan the purchased count must be an integer in `1…1000` — including from an injected dependency — or it contributes 0. The owner-approved model is unchanged (working 2/3/5/10, viewers 2/5/10/50, extra working seat EUR 15/15/12/10).

**Seat purchase, upgrade and downgrade mutation is deliberately NOT implemented.** Nothing in the product can increase the purchased count; only a reconciled Stripe projection can. That remains open work and is not accepted here.

## Narrow security correction — inherited table privileges and a strict retention boundary

One bounded correction on top of the stage above, from newly verified environment evidence. It is **not** a new feature or a new scope: the `20261028183000` migration is **still unapplied**, no commercial SQL has been applied anywhere, and public paid activation stays held.

**The problem.** RLS is not isolation for a role that bypasses it. Production carries a named `sandbox_exec` role that is `LOGIN` and `BYPASSRLS` and **not** superuser, and the `public` schema's DEFAULT PRIVILEGES (owner `postgres`) grant it `SELECT` and `INSERT` on **every newly created table**. The migration's revoke named only `PUBLIC`, `anon` and `authenticated`, so all five sensitive stores would have inherited a real read **and write** right the moment they were created, RLS notwithstanding. Root's strict production installation wrapper detected exactly this on a **separate** bounded migration and rolled that transaction back completely before commit.

**The fix, and its limits.** The migration now detects that **optional** role and, only when it exists, `REVOKE ALL PRIVILEGES` on exactly `stripe_customers`, `stripe_subscriptions`, `stripe_webhook_receipts`, `stripe_account_leases`, `stripe_checkout_requests` from it. It then **verifies the end state instead of trusting the revoke** and fails closed (`stripe_lifecycle_table_privacy_incomplete`) if any effective classic table right, any effective column right, or **any** direct ACL entry for that role remains; the ACL-entry test is privilege-name-free (`aclexplode` + `regrole`), so a right not enumerated here — `MAINTAIN` on 17, or anything later — is still caught without naming a keyword an older server would reject. It creates, alters or drops no role or membership, does **not** touch DEFAULT PRIVILEGES, and changes no other table, policy, RLS setting, grant or historical migration. Where the role is absent it is a documented no-op. A revoke alone would not have been enough: inherited membership or a role attribute could still grant access, which is why the postflight check is part of the same transaction.

**Function privileges are unchanged, and deliberately so.** Root independently read the function defaults at **2026-10-28T21:15:41Z**: for the queried `public`/global defaults owned by `postgres` and `supabase_admin`, public function `EXECUTE` defaults grant `postgres`/`anon`/`authenticated`/`service_role`, with **no** direct `sandbox_exec` or non-standard grant and **no global default row observed**. That is the observation, not a proof of broader absence. The existing explicit `PUBLIC`/`anon`/`authenticated` function revoke is therefore required and remains exactly as it was, and no global or default permission was rewritten. Acceptance checks the consequence rather than the text: `sandbox_exec` has `EXECUTE` on **none** of the 22 new RPCs and an actual call is refused, while `service_role` keeps all of them.

**Required before any later production migration (still open).** This protection covers the one role name that was actually observed. Before applying in production the strict wrapper must, **after** apply and inside the same refusable transaction, verify per sensitive table: no effective classic or column right and no direct ACL entry for `sandbox_exec` **or any other non-`service_role` grantee**; the schema's DEFAULT PRIVILEGES unchanged; RLS on with zero policies. The live role inventory must be re-read at apply time — a differently named inheriting role would need the same treatment, and nothing here detects one.

**Strict idempotency retention boundary.** Stripe's current primary documentation ([error handling — idempotency](https://docs.stripe.com/error-low-level#idempotency), verified through the connected Stripe documentation search) states keys are retained for **at least** 24 hours and may then be removed, and that reusing a removed key executes a **new** request. The local retry guard therefore requires elapsed time **strictly less** than 24h: at exactly the request's immutable creation time + 24h the attempt is fenced (non-terminal, slot held) and no customer or Checkout `POST` is dispatched. The stable idempotency keys, the other guards and the approved retained behaviour (a dispatched customer stays created and mapped) are unchanged. This is verified by local synthetic clock tests only.

**Acceptance distinctions are unchanged.** This is **foundation** acceptance: prepared code with local PGlite and mocked tests, including synthetic role fixtures that never connect to a real database or provider. **Sandbox** acceptance still requires a company-owned Stripe test environment, which does not exist in the authorized scope. **Production** acceptance has not been performed and is not claimed — the migration is unapplied, and neither R21 nor commercial production acceptance is complete.

## Honest limitations

1. **Route registration — resolved by Codex, not by this packet.** The earlier single `tsc` error (`src/routes/api/public/webhooks/stripe.ts(14,38): TS2345`, `'"/api/public/webhooks/stripe"' is not assignable to parameter of type 'keyof FileRoutesByPath | undefined'`) is gone: Codex **ran the generator** and retained the 22 necessary generated registration lines for `/api/public/webhooks/stripe` in the original route order — a recorded integration exception, not a hand-authored route tree — so the route is registered and `npx --no-install tsc --noEmit` is clean. Regeneration happens on `vite dev`/`vite build`; no Claude stage has edited that generated file. **Registered is not reachable in any useful sense yet**: there is still no configured account, key or webhook secret, so the endpoint answers `503 Webhook not configured`, and nothing has ever been delivered to it.
2. **Nothing is verified against Stripe.** No account, product, price, key, webhook endpoint, customer, session or subscription was created or inspected. Root verified independently that the company account `acct_1UG25BR3iZxco14q` has **0 managed sandboxes**, and no sandbox credential exists in the authorized scope; none was configured or created. Every provider shape in the tests is a synthetic fixture written from documentation, so a schema detail could still be wrong in a way local tests cannot detect. In particular, **recovery assumes `GET /v1/checkout/sessions?customer=…` returns the session carrying our `client_reference_id`**; that filter behaviour is a documented assumption, not a verified one.
3. **A fenced request is recovered only by retrying the identical request.** Recovery runs when the same `requestId` arrives with the same selected parameters (what a retrying client naturally sends). A caller who instead changes plan or seats, or starts a fresh `requestId`, gets `request_unavailable` while the fenced slot is held, and the slot stays held until the identical retry or an operator settles it. `stripe_read_checkout_request` exists as the operator-facing read for that case; there is no self-service "release my blocked request" path, deliberately.
4. **Recovery is bounded by one page.** Fenced-request recovery and every duplicate check require a complete list within one 100-item page. A customer with more than 100 Checkout Sessions or subscriptions can never be proven complete, so such a request stays fenced for an operator instead of being released. That is deliberate (fenced is safe) but it is a real operational gap.
5. **An `active` subscription with an authoritatively unpaid invoice stays uncertain forever** rather than being revoked or granted, until Stripe moves it to a non-granting status or the invoice is paid. With the attempt limit that means such a receipt eventually waits for an operator. Chosen over flapping an entitlement on in-flight payments.
6. **The replay has no scheduler.** It is an explicit, bounded, service-only call. Without an operator or service task, recovery relies on Stripe's own retries plus the durable receipt.
7. **Account verification requires permission.** Every reconciliation and every mutation reads the account object. If the restricted key lacks that permission, processing stays uncertain and nothing is granted — deliberately conservative, but the key must be provisioned for it.
8. **Not implemented at all:** seat purchase/change mutation, proration, plan switching, refunds, credit notes, tax, invoice presentation, dunning copy, subscriber migration from Paddle, and any UI. The entitlement statuses written are limited to `active`, `pastDue`, `cancelled` and `freePreview`.
9. **Test counts are local.** They demonstrate the decision logic and the SQL contract, not revenue correctness. No live acceptance has been performed and none is claimed.

## Status correction — superseded by the commercial operations stage (28 October 2026, revised 29 October)

Three statements above are now out of date. They are corrected here rather than rewritten in place, so the foundation's own reviewed text stays intact.

1. **The projection is no longer called directly.** `stripe-lifecycle.server.ts` now calls `stripe_commercial_guarded_projection` (added by the additive migration `20261028223000`), which takes the same fenced lease, runs in the same transaction, refuses to **widen** an allowance while a paid plan/seat change is unresolved, and otherwise delegates to `stripe_apply_subscription_projection` **unchanged**. The foundation function and its grants are not modified. Consequence and release gate: **both migrations must now be applied together** — applying `20261028183000` alone leaves the webhook unable to project. The new outcome `operation_pending_hold` is treated as uncertain (nothing written, receipt retryable).

   **What the gate measures against (revised).** The threshold is the pending operation's **immutable, re-proved allowance baseline**, captured once when the operation is created and never updated — deliberately **not** the latest observed `stripe_subscriptions` row. That row records the latest OBSERVED state, granting or not, so a legitimate non-granting observation of a larger plan rewrites it; comparing against it made the threshold movable, and a granting projection could then compare equal and pass while the operation that pays for it was still unresolved. `baseline_known: false` is an explicit HOLD of every granting projection, not a zero allowance. Capture and the gate are serialized by a shared owner/account/mode advisory lock. Historical seat entitlement is not separately stored anywhere and nothing reconstructs one.

   **The adapter's own half, unchanged in behaviour and now explicitly tested.** `decideProjection` already stopped uncertainty _before_ the projection, and that is the invariant the commercial gate depends on: a LIVE `active`/`trialing` subscription that looks paid and current but whose items or payment evidence cannot be read exactly returns `uncertain`, so **zero** projection calls are made and the receipt stays retryable. A grant-shaped live snapshot is never passed with `p_grants: false` — the only `grants: false` path requires an explicitly revocable status — because doing so would overwrite the observed row with a bigger plan while granting nothing. Legitimate non-granting observations (`past_due`, `unpaid`, `canceled`, `incomplete`, `paused`) still apply normally, and test-mode observations still write no live entitlement. No foundation logic was changed for this; the server stage added the regressions that pin it.

   **The two halves are now joined by one executed integration fixture.** Caller-level checks against a mocked RPC and direct checks of the guard with handwritten arguments each prove their own layer only, so the review-correction stage added a fixture that runs this module's **exported** `receiveStripeWebhook` against the frozen SQL in synthetic LIVE mode — a real mapped customer, a trusted growth/0 projection, a live entitlement and a pending operation created through the accepted RPC — with every guard argument computed by the production reconciler. Executed locally: a grant-shaped live snapshot whose evidence cannot be read makes **zero** projection calls and leaves both the observed row and the entitlement byte-unchanged; a legitimate non-granting `past_due` pro/4 really applies and narrows the entitlement (the gate must never block a revoke); the subsequent **paid, future, granting** pro/4 is held with nothing written, the frozen baseline unchanged, the receipt left `uncertain` and the entitlement not widened to the observed plan; the baseline allowance itself still grants; an unprovable baseline holds every grant; and a test-mode delivery projects only into test-mode rows. No grant-shaped live snapshot is fabricated with `p_grants: false`, no live credential or network is involved, and no historical seat storage was introduced.

   **One additive change inside this module.** `StripeLifecycleError` now carries a `detail` field, set in the RPC helper from the underlying database/transport message. `code` is unchanged (`<rpc>_failed`) and every existing caller still matches on it; `detail` exists so one caller can tell a DETERMINISTIC SQL rejection (a `RAISE EXCEPTION` the frozen functions define) from a transport failure that proves nothing — the commercial refund path uses it so an ambiguous `reserve_refund` error can no longer become a terminal refusal. It is never returned to a caller and no decision in this module reads it.

2. **"Seat purchase, upgrade and downgrade mutation is deliberately NOT implemented"** (Seat reads) and **"Not implemented at all: seat purchase/change mutation, proration, plan switching, refunds"** (Honest limitations 8) are superseded for the dormant backend: plan and seat changes with provider-calculated proration, cancellation and its reversal, and operator-approved support refunds now exist as **held, test-mode-only** code with local tests. Still not implemented: tax, invoice presentation, credit notes, dunning copy, Paddle subscriber migration, any UI, and dispute/early-fraud/risk-event handling. Nothing in the product can still increase the purchased seat count without a reconciled Stripe projection.
3. **The "Refund / dispute" sandbox row** ("acknowledged only, no entitlement effect — needs an explicit decision") has its decision: a refund has **no** entitlement effect, ever. Subscription and access effects are the approved case policy plus authoritative provider state, and a cancellation is a separate explicit operation. Disputes remain unhandled and are recorded as a release gap.
