# Stripe commercial operations — dormant backend stage (28 October 2026, server completion and billing UI 29 October)

**Status: prepared code with local tests only. Every live financial mutation stays HELD in code, and nothing here is sandbox or production acceptance.** This stage creates no Stripe object, consumes no credential, touches no production data, sends no message and activates no billing. Live plan changes, seat changes, cancellations, reversals and refunds are refused by code constants before any provider or database access. The sandbox owner allowlist is still **empty by default**. Manual beta/comped access, legacy Paddle subscriber management, existing entitlements and the isolated legacy sandbox adapter are unchanged. The USD 50/month global AI ceiling and the manual-budget prerequisite for free accounts are untouched.

There is still **no configured isolated sandbox**: no company-owned Stripe test environment, account id, restricted key, price or webhook secret exists in the authorized scope, so no end-to-end path has ever run. Local unit tests and a PGlite migration harness prove the _decision logic and the SQL contract_; they prove nothing about Stripe's own behaviour.

This stage delivers dormant backend support and executable local acceptance for plan/seat changes with proration, cancellation and its reversal, and approved support refunds. **It does not constitute real sandbox acceptance or R21 completion.**

### Trust boundary (the foundation's, extended)

- **No direct table WRITES from TypeScript, plus two narrowly scoped service-only SELECTs.** Every database _mutation_ is a `SECURITY DEFINER` function granted to `service_role` only, with RLS enabled and no policies. The single-open-operation rule, the monotone state machine, the quote binding, the refund reservation arithmetic, the once-per-plan guarantee and the projection gate cannot be bypassed from application code. Two read-only exceptions exist, both through the service client and both over a fixed column list scoped to the exact row plus the authenticated owner / verified account / mode: the operation's immutable original terms, and the refund reservation's durable state (see limitation 13). They write nothing and nothing they return reaches a caller. An earlier revision of this document claimed "no TypeScript table access" without qualification; that overstated the boundary and is corrected here.
- **Nothing from the client is authority.** The owner comes from the authenticated session; the account, mode, customer, subscription, item ids, prices and every monetary amount are server-resolved. The caller may send a target plan, a seat count and the amount it displayed — and that amount is only ever **compared** with the durable quote. A customer, account, mode, subscription, price, item or owner id in the request body is rejected by the strict validator, and so is an `approved` flag.
- **The market comes from the persisted billing country**, read on the server from `workspace_meta.billing_profile`. That JSON is user-editable, so the country is validated, the market is derived server-side (never from a UI locale or an unvalidated client market), and the result is compared with the currency the paid subscription is actually locked to. An unknown, unlisted or review-flagged market is held, and an attempted currency switch is held — this packet does not move an existing subscription to another currency.
- **A successful HTTP status grants nothing.** An increase requires both halves: the subscription items authoritatively carrying the target **and** the exact update invoice authoritatively paid. The POST response body supplies exactly one thing — the identity of the invoice this update raised, which is then recorded durably and read back independently; it establishes no outcome.
- **Uncertainty is non-terminal.** Past Stripe's 24h idempotency retention an unknown outcome is **fenced** (slot held, zero dispatches); only an authoritative read may settle it.
- **A false or thrown database write is never success.** The three outcomes of every durable write are kept apart: SQL `true` (it happened), SQL `false` (the compare-and-set was rejected, nothing was written, another instance owns the state) and an exception (unknown). An unknown is resolved only by re-reading the exact scoped row; otherwise the caller gets recoverable uncertainty. Every `advance`/`finish` supplies an explicit expected state, so a stale worker cannot move or close an operation another instance has dispatched.
- **An unchanged subscription is not evidence of a non-dispatch.** A post-dispatch fingerprint that still matches — including after retention expiry — is UNKNOWN, not proof. A concurrent provider request may still complete, so such an attempt is held/fenced and never settled `failed`, which would release the projection gate for a change that then lands.

### The projection gate (why this is not a standalone helper)

`stripe_commercial_guarded_projection` is now the webhook path's only write entry point. It takes the **same fenced lease**, runs in the **same transaction**, and adds exactly one rule: while an unresolved `plan_change`/`seat_change` operation holds this owner's slot, a projection may not **widen** the allowance.

The threshold is the operation's **immutable, re-proved allowance baseline**, captured once at `begin_operation` and never updated — deliberately **not** the latest observed `stripe_subscriptions` row. That row records the latest OBSERVED state, granting or not, so a legitimate non-granting observation of a larger plan (an observed `past_due` pro/4) used to rewrite it and thereby raise the bar: the next granting pro/4 then compared equal and passed while the operation that pays for it was still unresolved. The baseline comes from `stripe_commercial_verified_baseline`, which re-evaluates the foundation's own grant predicate (sellable plan, grant-eligible status, paid latest invoice, present/finite/future period, known seats, this exact subscription, and in live mode a consistent Stripe entitlement), and capture is serialized with the gate by a shared owner/account/mode advisory lock.

What is held: a granting projection whose plan rank or seat quantity exceeds that frozen baseline; one naming a different subscription than the pending operation or its baseline; one whose plan this policy does not recognise; and **every** granting projection for an operation whose baseline could not be proved. `baseline_known: false` is an explicit HOLD — not a zero allowance, not a smaller plan to assume, and not a signal to pick fresh prices. In those cases **nothing is written** and the receipt is left `uncertain` (retryable), so the previously verified allowance and its entitlement survive byte for byte.

What is deliberately **not** held: equal projections, decreases, and every revoke/non-granting projection. A cancellation or a payment failure during a pending change must still take effect.

This closes the specific risk that a paid **historical** invoice, a stale redelivery, an out-of-order delivery, an incomplete SCA flow or a replay could be reconciled into a bigger plan or seat count. It is enforced in SQL because a TypeScript check before a separate write would be a time-of-check/time-of-use gap. `pendingChangeWouldWiden` in the pure module mirrors the rule for reasoning and testing; **the wrapper is the enforcement**.

The adapter's own half is that uncertainty must be stopped **before** the projection. A LIVE active/trialing subscription that looks paid and current but whose exact evidence cannot be read produces **zero projection calls** (a retryable `503`), and a grant-shaped live snapshot is never passed with `p_grants: false` — doing so would overwrite the observed row with a bigger plan while granting nothing, which is exactly how the bar used to move. Historical seat entitlement is not separately stored anywhere, and nothing here reconstructs one.

Both halves are now joined by one integration fixture rather than inferred from two layers: the **exported** `receiveStripeWebhook` runs against the frozen SQL in synthetic live mode, over a real mapped customer, a trusted growth/0 projection, a live entitlement and a pending operation created through the accepted RPC. Every argument the guard receives is the one the production reconciler computed. A legitimate non-granting `past_due` pro/4 is applied and narrows the entitlement — the gate must never block a revoke — and the subsequent **paid, future, granting** pro/4 is held with nothing written, the frozen baseline unchanged, the receipt left `uncertain` and the entitlement not widened to the observed plan; the baseline allowance itself still grants. An unprovable baseline holds every grant, and a test-mode delivery projects only into test-mode rows. Caller-level checks against a mocked RPC and direct guard checks with handwritten arguments remain useful at their own layers, but they cannot substitute for this one.

**Consequence, and a release gate:** both migrations must now be applied together. With only `20261028183000` applied, the wrapper does not exist and the webhook cannot project.

### Plan and seat changes

**Preparation** resolves everything on the server in the only safe order — the hold, configuration, the caller's own mapping, the persisted billing country, the verified key-owning account, then the authoritative provider read — and has the **provider** calculate every amount. No provider mutation happens; the only POSTs are the previews.

**Two separate previews, two separate meanings.** They are not interchangeable and the backend keeps them in distinct fields:

- the **immediate** preview (default `next` preview mode) carries the quote's stable `proration_date` and `proration_behavior=always_invoice`, and its `amount_due` is what the customer pays **now**. Its lines must all be prorations of this change and at least one must sit on that stable date; a preview that mixes upcoming **renewal** lines into the figure is HELD (`preview_renewal_lines_present`), because no documented field separates "charged now" from "charged at renewal" inside one `amount_due`. A line that expresses neither the `proration` boolean nor `parent.subscription_item_details.proration` is `preview_line_proration_unknown`, not a guess. The two markers describe the same fact, so when both are present and **disagree** the line is `preview_line_proration_conflict`, and when either is present but **not a boolean** — including a present `null` — it is `preview_line_proration_unreadable`. A present malformed field is not the same thing as an absent one, and believing the other marker let `proration: true` with a nested `"false"` be charged immediately and a legacy `"true"` with a nested `false` be accepted as a recurring estimate. `null` is no different: a property whose value is null has been stated, and what it states is not the required boolean, so nothing in the documented contract makes it an alternative spelling of "this form is not used". A single marker is believed only when the other property is **genuinely absent**. All of them hold at the **preparation boundary** with no quote issued and no operation created;
- the **recurring estimate** is a second request in the documented `preview_mode=recurring`, with **no** proration date and no proration parameters — prorations, cancellations, trials and pauses are not supported in that mode. The official definition calls it a **long-term recurring bill estimate**: recurring items, their taxes and repeating/forever coupons. It is explicitly **not** the next exact debit, because one-time items and one-time discounts differ. The figure is the provider's `total`, never `subtotal` (which the Invoice object defines as the line sum **including** prorations and **before** invoice-level discounts and exclusive tax); when the two differ the difference is reported as a flag rather than itemised, and no arithmetic is synthesised. `recurringEstimateNote` travels with it so no caller can present it as a promised charge.

**The preview reason codes above are the pure reader's own, and the caller sees them DOUBLE-PREFIXED.** `prepareSubscriptionChange` prefixes `preview_` again when it forwards a preview failure, and the caller function forwards that string unchanged, so the values a caller actually receives are `preview_preview_line_proration_conflict`, `preview_preview_line_proration_unreadable`, `preview_preview_line_proration_unknown` and `preview_preview_renewal_lines_present`. That is recorded here as the exact caller contract rather than renamed: the strings are already asserted by the tests, and a rename would be an API change outside this stage.

A **period-end reduction takes no immediate preview at all**: nothing is charged now. A perfectly ordinary positive upcoming renewal is therefore not an immediate charge, and a reduction with zero to pay now and a positive recurring estimate succeeds. (Rejecting any positive `amount_due` from a `next`-mode preview refused legitimate reductions; that is corrected.)

- The exact current item state is read more strictly than the foundation's grant reader, because a mutation needs the real `si_…` item ids: an unreadable item id, a paginated item list, a second base item, a base quantity other than 1, a foreign seat plan, an elapsed period, an unsupported collection method or an unreadable schedule link all refuse the whole read.
- A **pending provider update**, an attached schedule, a pending cancellation, an unchanged request or a **mixed** request (plan up with seats down, which would need two effective dates in one confirmation) are all held.
- The configured provider price is validated against the owner-approved catalogue — currency, product, interval, interval count, active state and **amount** — before a quote may be issued. `PLAN_PRICING` and `PLAN_SEATS` are unchanged (working bundles 2/3/5/10, viewers 2/5/10/50, extra working seats EUR 15/15/12/10; reviewers consume working seats). AI and seats belong to the business account across its plan's project bundle.
- Extra working seats are offered **only in the approved EUR markets**. The research document's "suggested market scaling" is an example, not approved numbers, so a PLN/SEK/DKK/GBP seat price would have to be invented; it is refused instead. The plan itself may still be changed in those markets.
- A **period-end reduction below what the account currently uses is a capacity conflict**, held at preparation and **re-checked at confirmation**. A plan is **three** bundles, and all three are checked: working seats, viewer seats and **projects**. The seat halves come from the released account-wide counter (distinct people plus pending invitations, so one person on several projects is one seat and an outstanding invitation is not free); the project half is the owner's own migrated `workspace_entities` project rows. A reduction that fits the team and still exceeds the target plan's project allowance was previously invisible, because the seat counter does not express the project bundle at all. Either half being unreadable is UNKNOWN for that half — an owner with no `workspace_meta` row has **unknown** project usage, never zero — and a non-integer, negative or absurd count is unknown too. Members, projects and their data are preserved; nothing schedules a silent removal and nothing allows an unreviewed over-limit transition. Automatic invitation billing remains prohibited. The target plan's `projectAllowance` and the held reason are surfaced in the backend outputs.
- The quote is durable, short-lived (15 minutes), single-use and bound to the owner, account, mode, exact subscription, a fingerprint of the exact observed item/status/period/pending-update/schedule/latest-invoice state, a fingerprint of the selected item ids and prices, a stable proration date, and the provider's amount and currency. A quote cannot be issued while an unresolved operation holds the slot.
- Returned fields are UI-safe only: currency, integer minor-unit amounts, times, the effective date and a plain-language effective-date note. No id, price, customer, subscription, account or key is returned.

**Confirmation** requires the customer to echo the target and the amount they saw; both are compared with the durable quote in SQL.

The SQL layer distinguishes `stripe_commercial_quote_foreign`, `_expired`, `_consumed`, `_state_changed`, `_tampered`, `_unknown` and `_unavailable`. The **caller-visible** codes are coarser: a confirmation that fails the server's own pre-checks returns `quote_unknown`, `quote_foreign`, `quote_unreadable`, `quote_tampered` or `quote_selection_changed`, and a consumption the SQL provably refuses collapses to a single `quote_refused` — which is also what is written to the operation's `refusal_code`, so the precise SQL distinction is **not** currently retained anywhere. The slot is released in each case, so the customer can simply prepare again. An earlier revision of this document listed the SQL names as if they were returned to the caller; that was wrong and is corrected here. Narrowing `quote_refused` into distinct operator-visible reasons is a possible later improvement, not a correctness gap: every branch is a refusal that dispatches nothing.

**A consumption whose response was lost is not a refusal.** `consume_quote` raises for a genuine rejection and for a transport failure whose transaction may already have COMMITTED, and the wrapper cannot tell them apart, so the exact owner/account/mode-scoped quote is re-read and only what that readback can **prove** is terminal: another operation holding `consumed_by` on an otherwise exact row, or an explicitly unconsumed quote whose TTL has provably passed.

**The whole row is validated before any verdict is derived from it, in either direction.** The readback is evidence or it is nothing: the consumption identity must be PRESENT and either an explicit `null` — the only supported statement that nothing has consumed the quote, since the column is a nullable uuid — or a supported UUID. An omitted property is not that statement, a malformed consumer identifies nobody, and an **empty or whitespace-only** string is not SQL `NULL`: accepting it as one let a degraded readback with a passed TTL close an unresolved operation on the expiry refusal. All of those are unreadable; the bound amount must have a genuinely readable integer representation, because `Number()` reads `null`, `false` and `""` as zero and a **zero-due** confirmation is a real case that must not be impersonated by an unreadable field; and every bound term must agree. Only then is "another consumer" a refusal or "this operation" a committed consumption. Reading the identity first meant a non-UUID consumer, or a valid other consumer on a row whose own terms could not be read, closed the operation under its `prepared` compare-and-set. `consumed_by` equal to this operation with every bound term agreeing means the write committed and the attempt continues. Everything else — an unreadable read, an **absent** row, a row whose required fields cannot be read, and a row whose bound terms disagree — is `quote_consumption_uncertain`: the operation stays `prepared` and recoverable, the quote is untouched, nothing is dispatched and the clean retry succeeds. Treating absence or a binding mismatch as proof of rejection burned a healthy approval and closed the operation on evidence that says nothing about this call; the binding and tamper comparisons that _do_ refuse are the fresh pre-dispatch ones. The strict retention deadline is re-taken **after** that readback, so a deadline crossed during it fences with zero POSTs instead of dispatching.

- **Increases** update the **existing base item id** with its explicit quantity 1 — never adding a second base — and update the exact existing seat item, delete it, or add exactly one approved seat item. They use `proration_behavior=always_invoice` with the quote's stable `proration_date` and `payment_behavior=pending_if_incomplete`, so an incomplete payment leaves the items unchanged with a `pending_update` set. SCA, a decline, a pending payment, an expired attempt and an unknown outcome all leave the operation non-terminal, and the SQL gate keeps the previous allowance standing.
- **The exact selection is persisted and recovered, never re-derived.** The canonical `plan#seats#baseItemId#basePriceId#seatItemId#seatPriceId` is written on the operation by `begin_operation` and must be re-asserted identically on every resume. A resumed attempt rebuilds its request from **that** string — proved against the durable quote's own selection fingerprint — so a changed price registry or a changed subscription item id cannot rewrite the original intent. The base id, base price, quantity 1, the existing seat id/price/quantity, a seat removal and a single newly added seat must all match what was confirmed; equal plan and seat **counts** are not proof, and a substituted `si_…` or price is reported as not applied.
- **The invoice provenance sequence is fixed.** `prepared → dispatching` precedes the immutable update POST; the response's subscription/mode/customer identity is checked and the invoice id is taken **from that response** (an expanded invoice object is accepted); then `dispatching → awaiting_payment` records `p_invoice` **even when the response already says paid**, so the origin is durable before any success is declared. Only then are the invoice and the subscription read independently. The captured id is append-only: a newer `latest_invoice` can never replace it, and an `awaiting_payment`/`awaiting_apply` row with **no** captured invoice is an inconsistent row that is held rather than settled from a plausible current invoice.
- **What that invoice must prove:** it is this owner's and this subscription's, in this mode and currency, raised by `billing_reason=subscription_update`, authoritatively paid through the foundation's single payment rule with `amount_remaining` zero and `amount_paid` **exactly** the quoted amount, and it is **not** the durable pre-dispatch baseline recorded on the first attempt. An unrelated paid renewal fails that, and so does a zero-due quote with an old, open or unreadable invoice — a zero-due change is proved by a paid invoice for exactly zero, never by the absence of a charge. An absent baseline is uncertainty, not permission; a supported result that created **no** invoice is held rather than treated as a zero-charge success. (Comparing against a freshly read subscription instead would break on a resumed attempt, which already carries the new invoice — that is why the baseline is durable and append-only.)
- **A lost update acknowledgment** is recovered only by an **identical retained replay**: same endpoint, same idempotency key, same encoded parameter multiset, rebuilt entirely from the durable selection and the original quote's stable proration date. Past retention there is no POST at all and the slot stays held. When payment is proved but the item application is pending the operation moves `awaiting_payment → awaiting_apply`; `awaiting_apply` never regresses, and a pending read issues no same-state transition.
- **A LATE original response is still this operation's evidence.** A concurrent recovery that observed `dispatching` may fence the operation while this instance's own update POST is still unanswered — and when that POST then succeeds, the capture's compare-and-set is legitimately stale. Discarding the response there threw away the only existence of this update's invoice identity, and past retention there is no admissible replay either, so an update that had really landed left a fenced row with no invoice that nobody could settle. The known original identity is now recorded against the state **actually observed**, under that state's compare-and-set, and only when the row records no invoice yet: it is append-only, it is this operation's own response rather than a plausible `latest_invoice`, it adds no provider call, and the settlement that follows is the same authoritative two-halves proof. The operation's immutable creation time — and therefore its deadline — is untouched.
- **Reductions** take effect at the paid period end with no refund of unused time. Adoption and the phase update are **two separate durable steps** with separate idempotency keys (`:adopt`, `:phases`), because `from_subscription` cannot be combined with phase modifications in one request. **Between them, the complete canonical phase request, the validated original settings, the fixed effective boundary and the target are persisted atomically with the adopted schedule id**, under an explicit `dispatching → awaiting_apply` compare-and-set, **before the first `:phases` POST** (`reduction_dispatch_payload`, append-once, bounded to 4096 canonical bytes, version 1). That stored document is then the only body any first or permitted retry may send, and the only expectation any read-back is verified against; the current registry, the current period and a later GET may not redefine the body, the start, the settings or the prices. `proration_behavior=none` is set at **both** the request level and each phase level (they are different settings); `end_behavior=release` keeps the subscription running after the final phase, and the reduced phase carries **no** `end_date` or `duration` — finite phases do not imply a cancellation and are not treated as one.
- **The original adoption reply is validated before anything is normalised away.** Only one arrangement is supported — the ordinary documented schedule for an automatically charged, untaxed, undiscounted subscription — recorded as ten `default_settings` terms, thirteen paid-phase terms and four item terms. The ordinary response's `automatic` default anchor and `self` issuer are **retained** (substituting fabricated nulls would record a setting the response never had); `automatic_tax` collapses to `false` only after checking `enabled === false` **and** a null liability **and** no further key; an item's legacy `plan` mirror is dropped only after confirming it agrees with `price`; `default_tax_rates` on the phase and `tax_rates` on an item stay distinct facts, both required empty. A phase-level collection or payment method that is an explicit **override** is restated in **both** canonical phases; an **inherited** null is restated in neither. A known unsupported setting (a trial, an enabled tax, a `send_invoice` method, a legacy source, non-empty metadata or tax rates, an application fee, on-behalf-of, transfer data) **HOLDS** — it is never dropped to obtain apparent compatibility — and so does an unknown new material setting, a missing required field and a field v1 cannot represent at all (phase or item `discounts`, any `billing_thresholds`, a phase-level `automatic_tax`, `pause_collection`). Nothing is defaulted and no fabricated null is accepted.
- **Reduction recovery is read-only wherever it can be.** A lost adoption acknowledgment before capture is recovered only by a strictly retained identical `:adopt` replay — a latest-schedule GET is **not** original-phase evidence, because it cannot show what the original phase carried. A lost capture acknowledgment is resolved by an exact scoped readback of the schedule **and** the payload before any POST; a compare-and-set loser may not send its own candidate body and dispatches only the durable winner's. A completed phase update whose acknowledgment was lost completes **read-only, with zero POSTs of any kind**, after a process restart, a period rollover and the expiry of idempotency retention. Both the original effective boundary and strict retention are re-taken immediately before every duplicable POST; a missed boundary is never moved to a new date and never authorises a late reduction. A missing payload, an unprovable pre-capture adoption, an unequal stored document or an unmatched read-back stays held — and an unchanged subscription or absent schedule after a dispatched attempt does **not** prove no effect, even past retention.
- The read-back is verified against the stored original terms on **both** phases: `end_behavior=release`, status, both boundaries at the fixed instant, `proration_behavior=none` on each, the schedule's unchanged default settings, each phase's material settings, and the **exact paid current phase items in order** as well as the reduced target. A changed current-phase price or quantity rewrites a period the customer has already paid for; that was invisible when only the future phase was compared. A **foreign** schedule is refused and never overwritten, and a schedule attached to the subscription is treated as a conflict only against an id this operation itself recorded — on a resume it may be this operation's own adoption, which only the retained replay can establish.
- A **changed payment cycle or an unsupported schedule arrangement is held for review** rather than guessed.
- Operations carry a stable durable id, parameter fingerprint and idempotency key that survive restarts and lost acknowledgments; a new operation may not bypass an unresolved one; attempts are bounded (25) and an exhausted operation keeps its slot for an operator rather than being discarded.
- The retention deadline is derived from the operation's **immutable** creation time, re-read against a **fresh** clock immediately before every duplicable dispatch, and compared **strictly** (`< 24h`), because retention is documented as "at least 24 hours". A `prepared` operation has provably never dispatched — the advance to `dispatching` precedes every POST — so past retention it is settled `failed` and the slot is released; past retention in any later state it is **fenced**.

### Cancellation and reversal

A caller-owned explicit request schedules cancellation at the **authoritative current period end**, verified by re-reading the subscription. **Access keeps following the paid period: this path writes no entitlement at all.** Only the webhook projection, from an authoritative non-granting status, may revoke — exactly as the accepted foundation already does.

**Both paths resolve their own durable operation first.** Returning success straight from the provider's current `cancel_at_period_end` flag used to strand the operation: a lost acknowledgment left it `dispatching`, holding the owner's single slot and the projection gate forever while the caller was told the cancellation was done; symmetrically, a reversal that had already succeeded reported a false `cancellation_absent`. The flag is still what the outcome is proved from — but only after the operation has been read, and what it means depends on the durable state:

- flag set + `prepared` (nothing dispatched) → the cancellation is somebody else's and this operation is refused `cancellation_preexisting` under a compare-and-set, rather than credited with it;
- flag set + `dispatching`/`fenced` → this operation's own POST landed and lost its acknowledgment, so the flag **is** its evidence and the operation is settled with zero new provider calls;
- flag absent + `prepared` on a reversal → there is genuinely nothing to reverse, which refuses **this** operation instead of stranding it;
- an `applied` replay is reported accurately and dispatches nothing; `refused`/`failed` stay terminal. A `finish` that returns false or throws is re-read and, failing that, reported as recoverable uncertainty — never as a completed operation.

An explicit reversal before expiry is bound in SQL to an **applied** `cancel` operation for this exact owner, account, mode and subscription, and one cancellation can be reversed at most once; a caller-supplied id can never manufacture one. A subscription the provider already shows as `canceled`/`incomplete_expired` is **not recreated**: it is refused outright, and no entitlement is reset anywhere on these paths. Both paths use the same durable idempotency, retention and recovery discipline, and both are reachable only through the new caller functions behind the dormant hold. **No UI integration is claimed** — billing UI is a separate explicit packet and no route is registered here.

### Account deletion

Existing public text promises that deleting an account ends the subscription. **No real production account-deletion orchestration was found** (only a mocked admin API reference in an auth-email retention test). This stage provides a safe, read-only, service-side pre-deletion barrier (`readBillingDeletionBarrier` / `stripe_commercial_deletion_barrier`) that deletes nothing, cancels nothing and touches no auth row. `blocked: true` means a deletion must not proceed — a live subscription, an unresolved operation or reserved refund funds — and an unreadable billing state is also `blocked`, never "safe to delete".

**Retained acceptance gap:** nothing calls this on a deletion path today, because there is no deletion handler to call it. A standalone helper is **not** proof that the public promise works.

### Operator-approved support refunds

A service-only path, consistent with the existing support-by-email policy. **There is no caller endpoint, and the test suite asserts that no exported function name matches `/refund/i`.** No end-user can initiate, approve or amend a refund, and no "approved" boolean crosses any boundary: the durable `stripe_refund_cases` row **is** the approval, and it must carry the trusted operator actor, case id, amount and currency, policy basis, the original request time and **separate** subscription and access dispositions. A missing or unrecognised basis or disposition fails a database CHECK, so neither can be inferred. Re-recording an identical approval is idempotent; changing any term of an existing case is a conflict, never an amendment. Dispositions this packet cannot honour (`cancelImmediatelyHeld`, `revokeOnRefundHeld`) are recorded faithfully and **refused at execution**.

Evidence requirements, all mandatory before any money moves:

- the invoice is this owner's (from the server mapping), in this mode, for this subscription, and **authoritatively paid** through the foundation's single payment rule — "invoice remaining paid" is not refund success, and a `paid` status without a real `paid_at` is unknown, not evidence;
- exactly **one** paid `InvoicePayment` links it to exactly **one** succeeded `PaymentIntent`, and that payment's received total equals the allocation to this invoice. `amount_paid` on an InvoicePayment is an **allocation**, so it can be smaller than the payment's received total; anything else is **held** (`payment_allocation_ambiguous`) rather than refunding another invoice's funds. Multiple paid InvoicePayments, an unsupported payment type and an incomplete list are all held;
- a **complete** refund list bounds the amount by the funds actually remaining, counting pending, requires_action, succeeded **and every unknown or unreadable** outcome;
- the published policy allows it, evaluated from the authoritative first-payment time (from a complete invoice history for the exact customer and subscription) and the recorded case request time.

Policy, preserved exactly: the first-payment full refund **requested** within 14 days, once per customer **and plan**, with the existing abuse exception removing the guarantee rather than creating a refund; no ordinary renewal or unused-time refunds; approved legal and outage exceptions may be partial. The once-per-customer-per-plan limit is a **PRIMARY KEY** in `stripe_refund_policy_uses`, spent inside the reservation transaction. No legal advice is given and no consumer term is changed.

Reservation accounting is conservative and **cross-case serialized** by a per-invoice ledger row taken `FOR UPDATE`:

```
remaining = allocated_paid
          − (all local reservations not authoritatively released)
          − max(0, provider_committed − local reservations with a known refund id)
```

Both halves matter. Counting only the provider's figure would miss a refund this system dispatched whose outcome is unknown (no refund id yet, so it cannot appear in any provider list). Trusting a known refund id to be covered by the provider's figure would, on a lagging read, free funds that are actually committed — **reproduced by the `frees the funds for a NEW case` test**, where a pending refund with a known id and a provider total of 0 would otherwise have let a second case over-refund the same payment.

Only an authoritative **matching** `failed`/`canceled` refund releases a reservation. `pending`, `requires_action`, `succeeded` and every unknown/absent/timeout outcome keep the funds held. The refund id, once recorded, cannot be repointed. Full and partial refunds use durable **per-case** idempotency (`milo-ref:<account>:<mode>:<case>`), and after a timeout recovery finds our own refund by its case metadata from a complete list. Two of our own refunds for one case is `refund_ambiguous`, never a guess.

**A complete EMPTY refund list is UNKNOWN, not a cancelled refund.** This is the decisive correction in this stage. The absence of an object does not prove that no refund exists: another execution of the same operation may still have a POST in flight, or the provider may simply not have published it yet. Fabricating a `canceled` status from an empty list released real funds and closed the operation `failed` while the money was on its way out. Now an empty list keeps the reservation `reserved` and the operation open or fenced, with **no** synthetic settlement, no release, no terminal state and no newly parameterised refund — **including past retention**, where the earlier POST may still complete. Beyond the original strict `<24h` window nothing is dispatched at all: only recovery and fencing, never a new financial intent.

**Exact amount and linkage are verified on BOTH the creation response and any recovered or refetched refund**, before any settle call and before any success is reported: the approved amount exactly (not merely positive), the currency, the PaymentIntent/Charge linkage and the case/operation identity. **The approved case is part of that identity on both paths.** The creation response used to be checked for amount, currency and payment but not for the case its metadata names, so a well-formed refund carrying another case's `milo_refund_case` — or none at all — settled this case's approved reservation; both now stop before any settlement, with the funds still reserved and the case still `approved`. A refund for the wrong amount never settles the approved reservation — the refund's identity is still recorded so a later recovery cannot be repointed, but the reservation stays held. Mode comes from the verified account plus the exact linked payment, never from a non-existent `refund.livemode`.

`settle_refund` returns the reservation's **state text** — `reserved`, `settled` or `released` — not a boolean, and that text is validated: an unexpected value, an unreadable response or an exception is uncertainty. It is idempotent for an already terminal reservation and never repoints a recorded refund id, so a **lost settlement acknowledgment** is resolved by repeating the identical settlement — a re-read of the same reservation, never a second refund. When **both** acknowledgments are lost the exact scoped reservation is read: if the settlement did commit, SQL holds its state text and immutable refund id, and that resolves the operation with no refund POST and no new reservation. Going straight to provider rediscovery left such an operation open indefinitely behind a complete empty list, with nothing left to discover.

**An ambiguous `reserve_refund` error is never converted into a refusal.** The same call raises for a deterministic rejection (an over-reservation, a spent case, a spent once-per-plan use, a mismatch, a released reservation) and for a transport failure that proves nothing, so the exact scoped reservation decides and the raised code is classified:

- this operation's own matching reservation → the write committed (or an earlier attempt made it) and the refund continues from it;
- somebody else's reservation on this case, or no reservation **together with** one of the frozen function's own deterministic rejection codes → a real pre-dispatch refusal, and only a still-`prepared` operation is closed, under its compare-and-set;
- no reservation and no proved rejection (a socket failure before the write) → `refund_reservation_uncertain`. The operation stays `prepared`, the approval stays usable, nothing is dispatched and the clean retry refunds once. Refusing there burned a healthy approved refund for a lost connection;
- any state past `prepared` → uncertainty either way. A dispatched refund is never closed because a read came back empty, which is what previously terminated an in-flight refund while its POST was still running.

**Only the EXACT requested terminal is success.** When the money moved and this instance did not close the operation, the durable row decides: `applied` is the success, `refused`/`failed` is reported accurately as `refund_settled_but_operation_refused`/`_failed` and never reopened, an open row gets one retry from the state actually observed, and an unreadable read is uncertainty. Collapsing every terminal into a boolean reported `succeeded` for an operation another worker had closed `refused`, and the next replay then contradicted it.

**A consumed or refused case is recoverable, not a new failure.** `reserve_refund` recognises an existing same-operation reservation **before** it checks the case state, so an operation whose refund provably succeeded and whose result response was lost replays its durable success with zero refund POSTs and no new reservation. Reporting `refund_case_consumed` for money that had already moved was a false failure; a consumed case with no reservation for this operation is still refused. A **refused** case is recoverable for the mirror reason: `finish_operation` is what marks a case refused, so that state means this case's own operation reached a negative terminal — and the exact persisted reservation and operation, not the mutable case status, determine the replay. A released reservation whose operation was never closed (the release committed, the `finish` was lost or failed) is resolved from that durable release with no provider mutation and no second reservation, and the replay reports the refund's own `refund_failed`/`refund_canceled` rather than a generic `refund_case_refused`. If the final closure itself cannot be proved, that is said: `refund_release_completion_uncertain` leaves the operation open instead of claiming it was finished.

The refund returns to the **original payment method** (no `payment_method`, `reverse_transfer` or `refund_application_fee` is ever sent), carries no customer-balance origin and no Connect-transfer operation, and sends no instruction email. **Subscription and access effects are the approved case policy plus authoritative provider state only**: a refund never grants paid access, never marks a cancellation done, and never writes an entitlement. A cancellation remains a separate explicit operation, and the dispositions are reported back unchanged. Published response (2 business days) and settlement (5–10 business days) copy is returned as copy, claiming nothing about execution.

### Database and permission boundary

Six new service-only tables with closed RLS and no policies: `stripe_commercial_quotes`, `stripe_commercial_operations`, `stripe_refund_cases`, `stripe_refund_invoice_ledger`, `stripe_refund_reservations`, `stripe_refund_policy_uses`. Exact scope and ownership, monotone states, bounded attempts, append-only evidence ids, the per-invoice lock and the transactional projection gate are enforced at the SQL boundary. The state machine is a small explicit transition table (`stripe_commercial_transition`), not a generic workflow framework: nothing returns to `prepared`, nothing leaves a terminal state, and `applied` is reachable only from a state that recorded a dispatch.

The same **inherited default-ACL** protection as the accepted foundation is applied, for the same verified reason: production carries an optional `sandbox_exec` role that is `LOGIN` and `BYPASSRLS` and not superuser, and the `public` schema's DEFAULT PRIVILEGES grant it `SELECT` and `INSERT` on every newly created table. The migration detects that **optional** role and, only when it exists, revokes everything on exactly these six tables from it, then **verifies the end state instead of trusting the revoke** — failing the whole install closed (`stripe_commercial_table_privacy_incomplete`) if any effective classic right, any effective column right, or **any** direct ACL entry remains. The ACL test is privilege-name-free (`aclexplode` + `regrole`). It creates, alters or drops no role or membership, does not touch DEFAULT PRIVILEGES, and changes no other object. Where the role is absent it is a documented no-op. `PUBLIC`/`anon`/`authenticated` function `EXECUTE` is explicitly revoked on all 21 new functions; `service_role` keeps them.

**Required before any production migration (still open, unchanged from the foundation):** the strict wrapper must, after apply and inside the same refusable transaction, verify per sensitive table that there is no effective classic or column right and no direct ACL entry for `sandbox_exec` **or any other non-`service_role` grantee**; that the schema's DEFAULT PRIVILEGES are unchanged; and that RLS is on with zero policies. The live role inventory must be re-read at apply time — a differently named inheriting role would need the same treatment, and nothing here detects one.

### The new read adapter

`readCommercialAccountSummary(userId)` is the single authority for billing decisions in the UI. `getMyEntitlementFn` is deliberately **not** used for this: it resolves a read failure to Free, and the mapper behind it normalises a malformed provider to Paddle and an unknown plan to Free.

It performs one owner-wide, read-only pass over `entitlements`, `stripe_customers`, `stripe_subscriptions`, `stripe_commercial_operations`, `stripe_checkout_requests` and (for a discovered operation) `stripe_commercial_quotes`, over named columns only, bounded at 100 rows per table with **truncation treated as "I could not see all of it"**. This is a third read-only exception to the no-table-access boundary in _Trust boundary_ above, and it exists because discovery has no RPC: `stripe_commercial_read_operation` needs an id the returning customer no longer has, and `stripe_commercial_current_subscription` answers for one account and mode only. It writes nothing, calls no provider, and returns only the opaque caller UUIDs plus the safe terms already shown.

What it returns, and the two things it refuses to invent:

- **The current billed amount is always `null` with `currentAmountEvidence: "unknown"`.** No local table holds it. A catalogue price, the editable billing country, the store's reconstructed `priceMonthly`, `latest_invoice_paid` and a previous quote are all refused as substitutes. The `"fixture"` evidence tag exists only so the browser harness can exercise the money presentation, and the screen labels it as such.
- **Unknown is not Free.** A failed, denied, truncated or malformed read is `{ ok: false }` or an explicit `provider: "unknown"` / `access: "unknown"`, never a verified free account and never a guessed provider.

Discovery returns at most one open operation with its original plan, seats, amount, currency, direction, effective date and expiry. Two open operations, an unreadable bound quote or an absent one are **ambiguous or unknown** — held, and never permission to create a replacement. A reversal is offered only for exactly one applied cancellation that no reversal already points at.

### The manual/Free guard

`evaluateManualEntitlementClearance(userId)` runs inside `setManualEntitlementFn`, **after** the existing owner-role check and for **every** manual status including the Free reset, because a disabled button protects nobody who calls the function directly. It holds the write for: any nonterminal projection in any account or mode (`active`, `trialing`, `incomplete`, `past_due`, `unpaid`, `paused`), any open commercial operation, any unresolved checkout or portal request, a completed checkout whose scope has no projection, a raw Stripe entitlement with no coherent terminal projection behind it, any malformed or unreadable evidence, and a blocking (or unreadable) `stripe_commercial_deletion_barrier`. It clears only a coherent terminal `canceled`/`cancelled`/`incomplete_expired` state or a clean absence.

For a raw Stripe entitlement, **granting no access is not the same as having ended**. The row's own status must also be terminal — `cancelled` or an explicit `freePreview` — because an `active` row whose period has merely lapsed, a `pastDue` row and a `checkoutPending` row all read as effective Free while the agreement behind them is still open. Terminal evidence is deliberately not reduced to `status === "cancelled"`.

No freshness window was invented: `observed_at` and `updated_at` mean different things and neither certifies current provider truth, so nonterminal evidence is held **regardless of age**. A valid test customer mapping alone neither blocks a legitimate manual or Paddle action nor changes the display provider. The barrier is a read, not an atomic lock over a later manual upsert — that limit is unchanged and is stated here rather than papered over.

### UI behaviour this stage actually implements

- Loading, unavailable, verified free and verified paid are distinct states. A transient refresh failure keeps the last verified facts visible with an honest warning; an identity change clears them; a response from an earlier request or an earlier user is discarded.
- The catalogue and the confirmed subscription are separate. Selecting another billing country changes the offer shown, not the agreement; saving it does not either.
- Provider routing follows the verified summary. Paddle keeps its existing caller-owned portal; `paddleCustomerId` in the store is no longer a routing signal. A Stripe "move me to Free" is a cancellation intent with its own confirmation and verified date, never a manual write.
- One deliberate confirmation per operation: mount, effects, Escape, Back, the overlay and dialog close dispatch nothing, and a double click before the first awaited response sends one request. An ambiguous answer keeps the same operation id and quote binding; reentry discovers that operation and offers only an explicit same-operation recovery.
- `amountMinor` and `recurringEstimateMinor` are shown separately, with the recurring figure labelled a long-term estimate. Zero is a real value; a missing amount is unknown. The server's English `recurringEstimateNote` / `effectiveNote` are **not** rendered — localized equivalents are, so a PL/SV/DA reader is never shown untranslated copy.
- No optimistic access. Pending, SCA, decline, uncertain and provider-applied all show "waiting for verification"; nothing writes a plan or seat count into the store and nothing calls the manual setter to simulate completion.
- Unknown and composed reason suffixes are never rendered, interpolated or logged; every known code maps to a finite localized string and everything else to a conservative fallback.

Corrected in the review-correction stage, after three independent reviews:

14. **A rotated price catalogue blocked recovery of an operation that was already dispatched.** The strict catalogue parser was the only way to read the subscription, so a price configuration that moved after dispatch made the original intent unrecoverable. The context is now three layers — authenticated identity, a **catalogue-free** snapshot for recovery, and today's catalogue/market eligibility for fresh intent only — and the applied-selection proof compares the operation's own durable item ids, prices and quantities. Recovery is not a catalogue bypass: a fresh intent under an unknown observed price is still refused, and owner/account/mode scoping is unchanged.
15. **A committed quote consumption whose acknowledgment was lost became a terminal refusal**, burning a valid quote and operation with nothing dispatched. The scoped readback now separates the two, and — the narrower residual — an **absent**, malformed or binding-mismatched readback is uncertainty rather than proof of rejection.
16. **A present but unreadable proration marker was treated as an absent one**, so a line marked `true` with a nested `"false"` was charged immediately and a legacy `"true"` with a nested `false` was accepted into a recurring estimate. Contradiction and unreadability now both hold, at the preparation boundary, with no quote issued.
17. **An ambiguous `reserve_refund` error could terminate a refund.** The original form closed a dispatched operation `refused` while its POST was still running; the narrower residual refused a healthy `prepared` approval whenever a transport failure was followed by a read that found no row. Only a proved deterministic rejection, or another operation's real reservation, now refuses — and only a `prepared` operation.
18. **A negative refund terminal was reported by its mutable case status, and its own completion was assumed.** A `refused` case short-circuited before the durable reservation was read, so a released reservation whose `finish` was lost could never be resolved; and a release reported `refund_failed` even when the operation's closure could not be established. The durable reservation now drives the replay, and an unprovable closure is `refund_release_completion_uncertain`.
19. **Only the exact requested terminal counts as success** (see _Operator-approved support refunds_): a different durable terminal is now reported as such instead of being collapsed into `succeeded`, and the creation response must name the approved case.

Corrected in the final residual-correction stage, after the successor delta reviews:

20. **A late original update response could strand the operation it had already paid for.** When a concurrent recovery fenced the row while this instance's POST was unanswered, the successful response's invoice identity was discarded with the stale capture — and past retention no replay could recover it, so the operation could never be settled by anyone. The known original identity is now recorded against the observed state (see _Plan and seat changes_). This was reproduced first, on one shared monotonic clock, and the fix is the minimum capture/recovery change under that state's compare-and-set.
21. **The consume readback could still produce a verdict from a row it had not fully read.** A non-UUID consumer, a valid other consumer on a row whose own bound terms were missing or disagreed, and an omitted `consumed_by` with a passed TTL all became definitive refusals; and `null`/`false`/`""` in the bound amount were read as a legitimate zero, which let a zero-due confirmation continue on unreadable evidence. The complete shape and the exact bindings are now validated before either verdict.
22. **A present `null` proration marker was treated as absence** (and a test had codified that), so the other marker was believed on the strength of a field that said nothing. Present-and-null now holds, in either position, while genuine absence of the property still allows the single-marker form.
23. **Three evidence defects in the tests themselves**, corrected rather than argued with: the parked-POST test gave each worker its own frozen clock and reset the call trace, so it counted a replay as "the original"; the adoption pair simulated a lost acknowledgment with a request that never had an effect; and the deleted-seat and explicit-override proofs compared a filtered view of one request instead of two complete bodies.

## Honest limitations and remaining gates

1. **Nothing is verified against Stripe.** No account, product, price, key, webhook endpoint, customer, session, subscription, schedule, invoice, payment or refund was created or inspected. Every provider shape in the tests is a **synthetic fixture written from documentation**, so a schema detail could still be wrong in a way local tests cannot detect. In particular these are **documented assumptions, not verified behaviour**: the preview endpoint `POST /v1/invoices/create_preview`, its `subscription_details[...]` shape and its `preview_mode=recurring` semantics; `GET /v1/invoice_payments?invoice=…` returning the modern InvoicePayment links; `GET /v1/refunds?payment_intent=…` filtering as expected; `subscription.pending_update` being present on an incomplete `pending_if_incomplete` update; `billing_reason=subscription_update` on the invoice an item update raises; the exact field set of the `from_subscription` adoption reply (ten default-settings terms, the ordinary `automatic` anchor, the `self` issuer, a null phase collection method, an item `plan` mirror); and schedule phase semantics for `end_behavior=release` with two phases and an open-ended final phase. If any is wrong the path **fails closed** (no quote, or a hold), but it will not work until a real sandbox confirms them.
   **Supported versus held, explicitly.** The one supported schedule arrangement is `automaticChargeNoTaxNoDiscount`. Everything else is HELD with its own reason rather than silently normalised: enabled tax, a non-null tax liability, `send_invoice` at either level, a legacy `default_source`, a `phase_start` or fabricated-null defaults anchor, a non-`self` or non-null phase invoice setting, trials, non-empty phase metadata / `add_invoice_items` / `default_tax_rates`, application fees, on-behalf-of, transfer data, phase descriptions, non-empty item `tax_rates` or metadata, an item `plan` that disagrees with `price`, an unknown new material setting, and any `discounts`, `billing_thresholds`, phase-level `automatic_tax` or `pause_collection` — which v1 cannot represent at all. A real sandbox that shows one of these on an ordinary subscription is a matrix entry, not a silent drop.
2. **Documentation could not be re-verified in this packet.** Network access to `docs.stripe.com` is denied in this sandbox, so the primary contracts listed in the packet were not re-fetched; the facts used are those already recorded in the accepted foundation and the packet itself. Nothing preview-only was adopted.
3. **Both migrations are unapplied, and now must be applied together.** Applying `20261028183000` alone leaves the webhook unable to project, because the guarded wrapper would not exist.
4. **Migration inventory integration is complete.** `20261028223000_stripe_commercial_operations.sql` is now enumerated in `src/lib/milo-candidate-chain-migration.test.ts`'s **`independentCandidates`** list — explicitly unapplied, with its own dedicated harness — so that chain no longer fails. The earlier "1 of 89 tests fails" note in this document is obsolete and has been removed. That file remains **outside this stage's write scope** and was not touched here.
5. **No scheduler, no replay for commercial operations.** Recovery is an explicit, bounded, service-only path driven by retrying the same operation id. An operation left unresolved holds the owner's slot **and** holds the projection gate against increases until it is resolved or an operator settles it. That is safe but a real operational gap, and it is the same shape as the foundation's "the replay has no scheduler" gap.
6. **Capacity enforcement at renewal is not implemented.** A reduction is blocked at preparation and re-checked at confirmation, but nothing enforces the reduced allowance when the scheduled phase actually starts. **Integration gate:** renewal-time seat enforcement (and the operator path for an account that grew between confirmation and the period end) is required before acceptance.
7. **Capacity is read through the released team-seat counter.** `stripe_commercial_membership_usage` reaches it via `to_regprocedure`, so an environment without that chain reports `known=false` and every reduction is held. Correct, but it means capacity depends on a migration outside this packet.
8. **Multi-payment and multi-invoice allocations are refused, not supported.** A payment that settled several invoices cannot be partially refunded by this packet. That is a deliberate hold with an explicit test, not a feature.
9. **Dispute, early-fraud-warning and risk-event integration is absent.** `charge.dispute.*` and `radar.early_fraud_warning.*` are not in the foundation's event allowlist and nothing here handles them, so a chargeback has no entitlement, reservation or operator effect. **Recorded as a release gap**, outside this bounded packet.
10. **Tax, invoice presentation, credit notes, dunning copy and Paddle subscriber migration remain unimplemented.** A billing UI now exists as prepared code with local tests and a local browser harness only (see _Billing UI stage_ above); it is not sandbox, payment or release acceptance, and it changes none of these gates.
11. **Test counts are local.** They demonstrate decision logic, the SQL contract and the server↔SQL interaction, not revenue correctness. No sandbox or live acceptance has been performed and none is claimed. No percentage, payment, refund or deployment outcome is asserted anywhere in this document.
12. **The recurring figure is an estimate, and the backend says so.** Nothing in this stage promises the exact next debit; `recurringEstimateMinor` carries `recurringEstimateNote` precisely so a later UI cannot quietly turn it into one. The amount actually charged now is the separate `amountMinor`, and for a period-end reduction it is zero.
13. **Two narrow service-only table reads exist.** Neither is a write path, and the enforcement stays in SQL.
    - `read_operation` deliberately omits the selection, the params fingerprint, the idempotency key and the quote identity, and a recovery has to re-assert the ORIGINAL selection to `begin_operation` before it can learn anything else — an ordering gap no RPC closes. It is closed by a single `SELECT` over the fixed list `state,kind,subscription_id,quote_id,selection_detail,idempotency_key,baseline_invoice_id`, filtered on `operation_id`, `user_id`, `account_id` and `mode`.
    - The refund reservation's durable state (`state,refund_id,refund_status,amount,currency,invoice_id,payment_id,operation_id`, filtered on `case_id`, `account_id` and `mode`) is read for two recoveries that would otherwise have to guess: an ambiguous `reserve_refund` error, where closing the operation would terminate an in-flight refund, and a settlement whose acknowledgment was lost twice, where SQL already holds the exact terminal result while the provider list may still be empty.

    Both are asserted in the SQL suite from the **production call site's own arguments** — the recorded `.eq` filters and column list — rather than from a handwritten query, including the cases where a valid persisted row belongs to another owner, account, mode, kind, subscription or quote and must therefore not be found. Every state change still goes through the RPCs; no table WRITE bypasses them, and none of these fields is ever returned to a caller.
