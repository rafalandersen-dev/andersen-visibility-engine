# P1.2G — Connector media behaviours (DESIGN, awaiting owner sign-off)

**Status: DOCUMENT ONLY. Nothing here is implemented. Each numbered decision
needs an explicit owner yes/no before any code is written** (spec §7 approval
triggers). Written 2026-07-24 after A/C/D/B/F/E/H shipped.

## What P1.2G adds
Publish the article's IMAGES faithfully per connector — today the assembled
HTML carries inline `<figure>` markup, but no connector sets a real featured
image at the destination, and republish never manages destination media.

## Decision 1 — WordPress featured media
Proposed: on publish of an asset with an ACTIVE featured image, upload the
controlled public object via `/wp/v2/media`, store `wordpressMediaId` on
`FeaturedImage`, set `featured_media` on the post. On republish: if the object
hash changed (`publishedObjectHash`), upload the NEW object, repoint the post,
and **detach but do not delete** the old media (delete risks breaking other
posts that reused it). Failure to upload media never blocks the post publish —
it downgrades honestly to "included: no" with a warning.
**Sign-off needed on:** detach-vs-delete of stale media; media upload failure =
warn-and-continue (proposed) vs block.

## Decision 2 — Shopify article image
Proposed: set the Shopify article `image` from the featured object on
create/update (single-image model — replace on republish, keyed by
`shopifyArticleGid`). Inline presentation classes are theme-dependent: report
`retained: unknown`, warn on size/alignment downgrades, never claim more.
**Sign-off needed on:** replace-on-republish (proposed) vs keep-first.

## Decision 3 — Custom endpoint payload extension ⚠️ highest risk
The custom-endpoint contract is LIVE in production consumers (Butelki
`milo-publish`/`milo-live` edge functions; Synergy `content_pages`). Proposed:
additive optional field `featuredImage: { url, alt, caption? }` in the draft
payload, behind a per-project flag `customPayloadFeaturedImage` that DEFAULTS
OFF — existing consumers see a byte-identical payload until the owner flips the
flag per project AND updates the consumer. No inline-image payload change in
this phase (assembled HTML already carries them).
**Sign-off needed on:** the additive field + opt-in flag approach; which
projects flip first (Butelki edge fn would need a matching update I can write).

## Decision 4 — Capability reporting
Extend the four-state model per destination with persisted evidence:
`wordpressMediaId` present → featured retained; a post-publish GET re-read →
destination-verified. Shopify: retained via the article response; verified via
re-read. Custom: never above "included" unless the consumer echoes receipt.
No sign-off concerns (honesty-only), listed for completeness.

## Security invariants (unchanged, restated)
Everything re-derived server-side from the owner's workspace (2.0
connector-guard invariant); only the controlled PUBLIC object is ever sent;
no client-supplied URLs; secrets stay in project settings server-side.

## Suggested order once signed off
WP featured media → Shopify image → capability evidence → custom-endpoint flag
(+ Butelki consumer update) — each its own reviewed PR.
