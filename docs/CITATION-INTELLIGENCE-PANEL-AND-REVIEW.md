# Citation Intelligence v1 — panel protocol, capture context and human review (CI-2)

**Status:** record design only (15 September 2026). Typed records and deterministic rules exist in `src/lib/citation-panel.ts` and `src/lib/citation-finding.ts` with tests. **No panel is locked, no storage, endpoint or UI exists, and nothing has been collected.** The Appendix A questions of `product/CITATION_INTELLIGENCE_SPEC.md` stay DRAFT until the owner reviews them; test fixtures use placeholder question text on purpose.

## Panel and session protocol (`citation-panel.ts`)

- `panelProtocolSchema`: an immutable panel version of kind `discovery` or `brand` with client market, question and interface language, one surface (service, interface, mode, search mode), the fixed session protocol (fresh session, personalisation, signed-in, memory, custom instructions, connected tools, no extra instruction, zero prior messages), the approved collection location (country, city, device-location permission, VPN/proxy state), up to ten question versions referencing existing `ai_visibility_prompts` ids and revisions, rounds, status and owner approval. The interface (UI chrome) language is fixed alongside the prompt (question) language, so collection on a different interface language is a methodology deviation. A locked panel needs approval; questions must be in the panel language (translations are reading aids); D-series ids belong to discovery and B-series to brand; a brand panel has zero rounds.
- `plannedSlots`: questions × one surface × rounds, so the Synergy discovery panel plans exactly forty slots and the fourth round is the re-test. Brand panels plan nothing; `brandRunSchema` records a separately approved diagnostic run with its own identity (`id`), observation budget and rounds. A brand capture's `brandRunId` must resolve to that run; a run without an id could not be told apart from a fabricated one.
- `surfaceSchema`: service, interface, mode and search mode, plus the locked methodology's expected model label (null when it pins none) and whether web search must be `evidenced`. The same schema describes the locked panel surface and each capture's observed surface.
- `captureContextSchema`: the extension to an existing manual answer record: panel and slot, brand run (null for discovery), actual session state, location (in the question, collection country and city, device permission, VPN), prompt/interface/answer language, actual surface and mode with model label and whether web search was evidenced, capture instant versus intended slot, exact question text, extra instruction and prior messages, screenshot reference and missing-data reason, and free deviation notes. No passwords, cookies, account email or tokens have a field.
- `protocolDeviations` and `slotOutcome`: a capture that claims a different panel id or version, a round outside the panel's planned rounds, a personalised/continued/re-instructed session, a different locked session control (sign-in, memory, custom instructions, connected tools), a changed surface, mode, prompt or interface language, or question text, a known model-label change (including to or from the unpinned null), a web-search-evidence state that differs from — or is unknown where the panel locks — the methodology, a changed collection location (a different collection country or city, a device-location permission change, or a VPN/proxy toggled from the locked state, with unknown never invented into a match), or a brand run on a discovery panel is a `protocol_deviant` slot. The prompt and interface languages are compared independently, each by strict equality, so an interface language recorded as unknown is never promoted into the locked expectation. The location _in the question_ is governed by the question text and is not part of the collection lock. Unknown-where-locked states never count as the locked success.
  - **Brand run resolution.** `protocolDeviations` (and `slotOutcome`) take the trusted set of owner-approved `brandRunSchema` runs, resolved server-side from storage — never asserted by the capture. A brand capture's `brandRunId` must resolve to a run in that set bound to this exact panel and version, the capture's round must fall inside the run's approved rounds, and — because owner approval is prospective — the run must have been approved no later than the capture's `capturedAt`; otherwise it fails closed (`brand_run_not_approved` for a missing, unknown, fabricated or unapproved run, `brand_run_panel_mismatch` for a foreign panel/version, `brand_round_out_of_run` for an unapproved round, `brand_run_approved_after_capture` for a run approved after — or with a timestamp unorderable against — the observation it would authorize), and a brand capture with no run at all is `brand_capture_without_run`. A run approved later cannot retroactively authorize an earlier observation, and an arbitrary well-formed UUID is not accepted; a future import/endpoint boundary must supply the approved runs from trusted storage, not from client input. Discovery and brand opt-in stay separate; nothing here schedules a brand run or expands scope. `slotOutcome` additionally binds a `complete` answer to the slot's *versioned* question: a complete answer whose `promptId` or `promptRevision` is not the slot question's — or that was captured under any protocol deviation — is `protocol_deviant`, never accepted on status alone and never promoted to an eligible complete capture. A genuine `failed` or `truncated` attempt keeps its own status even when the methodology also deviated or the prompt binding is wrong: the quality outcome is reported as itself, not masked as a mere `protocol_deviant` slot (it is never an eligible complete capture, so surfacing it inflates no denominator). An absent capture is `missed`.
- `panelCounts`: descriptive counts with explicit denominators per outcome: own-site citation present x of n eligible captures (complete answer, complete citation list, reviewed), mention and recommendation counts, partial positive citations kept separately, unreviewed captures counted as unreviewed, never as zero. Planned versus recorded slots are shown. It rejects an ambiguous capture set — a question outside the panel, a discovery round outside `1..rounds`, or two records for one slot — rather than silently keep favourable evidence, so denominators are never inflated. A brand count binds every capture to the one approved run it names via the capture's own `brandRunId`: all captures in a count must name the *same* run, and that run must resolve to an owner-approved run for this exact panel and version (trusted evidence, not asserted), whose approved observation budget and rounds then bound the whole batch. A run-less capture (missing identity), a mixed batch that names more than one run, or a run that is unknown, fabricated, unapproved or bound to a foreign panel/version fails closed — so no number of individually valid-looking brand captures can overrun the owner-approved observation ceiling, land on a round the run never authorized, or borrow a second, larger-budget approved run to legitimize captures that belong to a smaller one; legitimately distinct approved runs are counted separately, one count each. Discovery carries no brand run: a discovery capture that asserts a `brandRunId` is contradictory evidence and is refused before counting, keeping discovery and brand diagnostics separate.
- `comparablePairs`: baseline/follow-up pairs need the same question complete, reviewed and citation-complete in two distinct rounds, a valid baseline-before-follow-up chronology, and a follow-up captured after two _distinct_ destination-verified improvements. It takes explicit evidence for this exact panel and client — scoped captures (with their own `captureId` and panel/client) and scoped findings — and resolves each improvement's `findingIds` and `baselineCaptureIds` against those actual records: a reference to another panel/client, a missing record or a duplicate alias is rejected outright, never trusted from a bare asserted id. Distinctness is *substantive* — task, or destination together with the approved version — so a clone of one change with a fresh UUID (or a duplicate task, destination or version) cannot pose as a second change. A `public_url` destination is compared by canonical URL identity (scheme and host case-folded, default port and fragment dropped, path and query kept exact; an invalid URL fails closed), so re-casing a host or adding the default port or a fragment cannot manufacture a second change; other destination kinds are opaque identifiers compared exactly. Each change must be verified strictly after the baseline it improves on, and _two distinct changes must be verified strictly before a given follow-up_ for that follow-up to be comparable. That gate is measured per follow-up, not as the maximum verification time over all records, so recording a later third improvement never retroactively invalidates an already-comparable historical pair, and duplicates or unrelated records never let a follow-up meet it. Because every eligible capture is a `complete` slot it already matched the locked surface (model label and web-search evidence included), so baseline and follow-up share one methodology. Every missing pair is listed with its reason; no eligible pair means no completed comparable re-test.
  - **Trust boundary.** `comparablePairs` independently derives only: identity and scope binding (each capture and finding must resolve to a record for this exact panel id, version and client), reference uniqueness (no duplicate capture/finding ids, no duplicate `findingIds`/`baselineCaptureIds` aliases), the verified-improvement chronology (each improvement verified strictly after every baseline capture it improves on, the follow-up captured strictly after its baseline and strictly after two _distinct substantive_ changes were verified — measured per follow-up, not as the max over all records), and the count of _distinct substantive_ changes. It does **not** re-derive a capture's `outcome`: `complete` is a trusted upstream status already produced by `slotOutcome`/`protocolDeviations` over the manual answer record, and `citationsComplete` and `ownCitation` are trusted human-reviewed facts carried on the capture. This helper works on already-parsed in-memory records; it is not an endpoint or storage parser and does **not** by itself validate arbitrary or untrusted client input. No such import/endpoint parser exists in this preparation PR (see `docs/CITATION-INTELLIGENCE-NATIVE-IMPORT.md`); a real one must re-establish those upstream statuses from trusted evidence before this gate carries weight. The proof loop is not circular: an improvement's verification (destination receipt + approved version + scoped finding and baseline) is established _before_ the retest, and the comparable follow-up capture must occur strictly afterwards, so verification never depends on the retest it enables.

## Human findings and review (`citation-finding.ts`)

- Two equal gap families: `citation_source` and `recommendation_accuracy`. Priority derives from harm, relevance and fixability on one scale; the family never sets it.
- `sourceSupportSchema`: attribution is not support. `supports`, `partly_supports`, `contradicts` and `unclear` require the inspected passage, its capture date and the reviewer; `not_checked` carries a reason and no passage. `passageAfterAnswer` flags a passage captured after the answer.
- `businessFactSchema` and `factAt`: dated owner-confirmed facts with validity windows; `accuracySchema` records `accurate_at_capture`, `incorrect_at_capture`, `outdated_now`, `unclear` or `not_checked` against a specific fact, so a later price change never rewrites an old answer's truth.
- `recommendationSchema`: `recommended`, `mentioned_only`, `explicitly_not_recommended`, `not_present`, `unclear`, with the exact passage and target for observed states and a suitability judgement (fits / does not fit / unknown).
- `findingSchema`: evidence references (answer, native or source), human entity confirmation (only a confirmed entity can be accepted; ambiguity stays visible), completeness copied from the capture (own-citation absence and `not_present` need complete data), observation separate from a labelled hypothesis, support and accuracy assessments, reviewer and optional second reviewer, decision and linked task. `isCompetitorOnlyCitationGap` is the confident negative comparison and needs complete data.
- `improvementSchema` and `isVerifiedImprovement`: an improvement links accepted findings, the existing task, the version-bound approval, the destination and a live verification (publication receipt, owner inspection or index inspection) dated after the approval. A *verified* improvement must also carry the baseline captures it improves on (a before/after claim needs a before); an unverified draft may still be recorded without them. Both the schema and the predicate enforce this. `verifiedImprovementCount` counts *distinct substantive* verified changes (task, or destination + approved version), comparing a `public_url` destination by canonical URL identity (host case, default port and fragment folded; path and query exact; an invalid URL fails closed) and other destination kinds exactly, so a clone with a fresh UUID — or one that only re-cases the host or adds a default port or fragment — does not add one; the panel/client binding of that evidence is enforced by `comparablePairs`.

## What is still needed before implementation continues

1. Owner review of Appendix A (ten Swedish discovery questions), the surface lock (proposed: ChatGPT Search, consumer web app, non-personalised fresh session) and the session controls. The first locked panel version is created only after that review.
2. Owner-confirmed dated business facts for Synergy before any accuracy finding is accepted.
3. Storage for panels, capture context, facts, findings and improvements as bounded extensions of the existing evidence tables (a later candidate migration), then the review UI. None of this is started.

The same slot validation runs independently in counting and retest pairing: duplicated or out-of-panel slots cannot be selected as a favourable pair. Pairing requires a locked, approved discovery panel and valid ordered round numbers inside its plan. An unapproved draft remains available for planning but its captures are protocol-deviant. Brand diagnostics require their own approved-run context and cannot pass this discovery retest gate.
