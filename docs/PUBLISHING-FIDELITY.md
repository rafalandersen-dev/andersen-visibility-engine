# Publishing fidelity and evidence

The Studio preview, HTML export, immutable publication snapshot and WordPress/Shopify outgoing bodies use the same assembled HTML. The shared connector argument builders carry this HTML after server-side workspace lookup, exact-version approval and source checks. Public RPC schemas strip supplied HTML; a caller cannot replace it. Manual draft/live paths and the scheduled runner share these transports. The original fallback renderer remains for low-level callers without an assembled asset.

FAQ schema now follows the rendered HTML, including list/table text boundaries, visible formatting and escaped literal source. It no longer independently removes Markdown syntax that the renderer displays or retains table separators that the renderer hides. Exact FAQ heading aliases cover the 24 existing EU content-language choices. Questions still require a question heading inside a recognized FAQ section and a nonempty answer before the next heading. Repeated questions are deduplicated, with at most 20 pairs. This uses the application's own safe renderer output, not arbitrary remote HTML or a general HTML parser. It does not introduce a new Markdown dialect: unsupported syntax retains the renderer's existing visible behavior.

Approved image figures, captions and featured presentations survive the WordPress/Shopify transport instead of being converted back from degraded Markdown. Existing image approval, origin, alt-text, source, author, breadcrumb and internal-path gates remain authoritative. Owner Markdown and presentation fields are not rewritten. Custom endpoints keep their existing Markdown-only contract; no HTML or JSON-LD fields are added there.

WordPress/Shopify publication fingerprints include an HTML-delivery revision. Existing approvals for those destinations require a fresh review, even where the current article has no image. Changed FAQ output can also change a publication fingerprint. No approval is granted or migrated automatically. Existing queue entries remain subject to the current-version check before transport.

The actual Studio checklist says that local content checks pass, then explains that saved approval, fresh sources and an eligible destination are still required. Generated schema and planned inclusion are distinct from a sent-payload or acceptance receipt. Missing connector configuration is unknown, not WordPress. Custom JSON-LD delivery is unsupported. Destination retention, live-page presence and rich-result appearance remain unverified. This new copy is available in English, Polish, Swedish and Danish.

Local payload-capture tests establish application output only. They do not establish CMS sanitization/theme behavior, signed-in acceptance, live-page retention, search eligibility or appearance, or complete R18/product-reference acceptance. No live CMS fetch or publication is part of this verification.
