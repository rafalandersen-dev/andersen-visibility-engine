# Outreach delivery integrity

Outreach drafts remain editable workflow records. Their status, `sentAt`, provider labels and delivery events do not establish delivery authority. The authenticated review endpoint reads the saved draft and returns a snapshot of the exact recipient, subject, body and step with a version fingerprint. The confirmation dialog freezes that snapshot. Sending requires both explicit acknowledgements and a matching current version; saved changes require a fresh review. Separate follow-up delays are included in the fingerprint. Follow-ups are never automatic.

The service-owned receipt table reserves each owner/draft/step once before provider I/O. Reservation uses the same owner workspace lock as workspace writes, compares the exact read revision, and atomically checks the account's configured 1–20 daily limit (default 5) and 30-day recipient cooldown. All three steps are unique. Unknown, dispatching and interrupted reserved attempts retain capacity even after the ordinary time windows. An uncertain attempt to the recipient holds later outreach. Reservations survive draft and project deletion; recreating an ID cannot permit replay. Up to 3,000 attempts are retained per account; capacity exhaustion holds further sending. Account deletion removes its private receipts.

The table has RLS and no direct application-role access, including service-role writes. Four service-only functions admit, authorize one dispatch, finish a receipt and read project-scoped history. The authenticated server derives the owner; the browser cannot supply a replacement receipt. A follow-up requires a service-owned accepted initial receipt for the same project and recipient, with the minimum configured delay elapsed. Browser timestamps cannot authorize it. Historical outreach logs conservatively hold old attempts and protect rate/cooldown calculations; legacy browser labels can hold an initial send but cannot authorize one.

After reservation, a second database gate checks the workspace revision, draft scope, current suppression list and unused unsubscribe token immediately before provider I/O. Only a successful once-only transition from reserved to dispatching authorizes the fetch. A lost RPC response never authorizes dispatch. Existing authentication, Resend configuration, sender/reply-to requirements, unsubscribe handling and kill switch remain in place. Changes after the final gate cannot recall an email already being dispatched.

Provider responses have a 20-second deadline through the body and a 16 kB body limit. Invalid encoding, JSON, receipt identity, unsuccessful status and network failures become a safe unknown outcome. Raw upstream errors/bodies are not logged or returned. There is no automatic or manual replay of a reserved step, regardless of the provider's idempotency retention. A valid acceptance receipt is stored before optional workspace/log mirrors. If receipt persistence itself is uncertain, the dispatching record remains held.

The Outreach page reads the complete bounded server-owned history for the selected account/project. It shows unavailable separately from empty, exact version, original recipient, step, dates and receipt ID. It retains attempts whose drafts were deleted. Refresh is read-only and never sends. An accepted receipt can be restored to an unchanged draft without provider I/O; concurrent edits or withdrawal prevent overwriting the draft. Reserved, dispatching, unknown and blocked states have no retry affordance. Older editable labels are explicitly unverified. All new controls and explanatory copy are available in English, Polish, Swedish and Danish.

“Provider accepted” does not establish inbox delivery, opens, replies, outreach effectiveness or verified link placement. Unknown attempts have no provider-reconciliation workflow in this release and remain held. This correction does not send real outreach, configure accounts/senders, activate providers, add schedules or automatic follow-ups, purchase placements, or close R15 supplier/refund/placement and D04 acceptance. Linkhouse's private adapter remains pending; no contract is invented. Static/local fixtures and technical release checks do not establish signed-in or live-provider acceptance.
