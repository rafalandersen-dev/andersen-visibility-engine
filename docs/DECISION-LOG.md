# Decision Log — 2026‑07 Product Audit & Strategy

Records what was decided, rejected, or postponed and why. **Last revised:** 2026‑07‑21. Cross‑refs: `ROADMAP.md`, `TARGET-ARCHITECTURE.md`, `PRODUCT-AUDIT-2026-07.md`, `AGENCY-BENCHMARK-SEMPIRE.md`, `ARTICLE-STUDIO-3.0.md`.

Each entry: **D#** decision · **status** (ADOPTED / REJECTED / POSTPONED) · rationale.

## Positioning

- **D1 · ADOPTED — Product is an "AI Growth Operating System", not an "agency replacement".** Canonical definition: *detects opportunities, creates implementation‑ready assets, manages execution, verifies deployment, demonstrates measurable business impact.* Agency replacement is a **benchmark** only. *Rationale:* the audit used the agency benchmark to expose gaps, but defining the product as a replacement over‑claims and mis‑frames the roadmap. Milo's edge is a growth OS with a closed loop, not a like‑for‑like agency substitute.
- **D2 · ADOPTED — Relationship services stay human/partner/managed.** PR, negotiated links, sponsored placements, and outreach *execution* are customer‑, partner‑, or Andersen‑Innovations‑managed‑service. Milo does find/brief/draft/measure around them. *Rationale:* these are relationship + media‑budget services; automating "placements" would force a dishonest guarantee.

## Roadmap ordering

- **D3 · ADOPTED — Article Studio 2.0 MVP is P1, not post‑90.** *Rationale:* article quality is the known product weakness and the strongest commercial differentiator vs a volume‑poor agency package (Sempire: 34k–100k chars/**year**). Size is not a reason to defer a differentiator.
- **D4 · ADOPTED — Corrected phase order:** P0 credibility/integrity → P1 commercial core (Article Studio + real content data) → P2 measurement/evidence (technical monitor, GA4/revenue, verification, reporting) → P3 advanced (AI Visibility, e‑commerce, entity, backlink monitoring/supplier). *Two genuine dependency notes recorded in `ROADMAP.md` §6* (Article Studio uses a lightweight URL inventory, not the P2 crawler; bounded metered source fetch, not the full monitor) — these scope the MVP rather than reorder it.
- **D5 · ADOPTED — "Turn on DataForSEO" is removed from P0** and placed behind the Cost‑Control Framework (P2.0) / P3.4. *Rationale:* see D8.

## Credibility & integrity (P0)

- **D6 · ADOPTED — No capability may claim measurement without measurement.** Modules that reason over the setup form are labelled advice/readiness; only real‑data modules are labelled measurement. Rename "Site Audit" and "AI Visibility"; add a fallback banner when the site could not be read. *Rationale:* the current framing is actively misleading (esp. on CSR SPAs like Synergy).
- **D7 · ADOPTED — Fix the Milo Score, preview parity, internal‑link integrity, and ship real JSON‑LD (P0.2–P0.5).** *Rationale:* the score grades ~36% of weight on fields it can't see; preview ≠ publish; invented internal links publish; `schemaSuggestions` promises structured data never emitted. All are integrity defects, cheap to fix.
- **D26 · ADOPTED — Internal‑link safety is a three‑state contract that BLOCKS publishing, not a silent drop (supersedes the first P0.4 cut).** Every relative in‑body link is VERIFIED, USER_APPROVED or UNRESOLVED. VERIFIED/USER_APPROVED publish as active links; an UNRESOLVED link is never sent as active **and never silently removed** — the author must explicitly approve this exact URL, replace it with a verified page, keep it as plain text, or remove it (no global "approve all"). The same rule governs all three connectors including the custom endpoint (`keepAllInternalLinks` removed); preview/export/publish share one effective state; approvals persist per‑path on `project.approvedInternalPaths` (JSONB, no migration). *Rationale:* the first P0.4 pass dropped every unverified relative link, which (a) contradicted the Milo Score's reward for in‑body links, (b) let the custom endpoint still send invented links as raw markdown, and (c) silently deleted **valid** customer URLs (`/services`, `/about`) that simply weren't in Milo's lightweight inventory. Blocking‑with‑choices is the only outcome that neither publishes an invented link nor destroys a real one. A sitemap inventory of existing customer URLs stays P1.1.

## External‑API safety

- **D8 · ADOPTED — External‑API Cost‑Control & Metering Framework (P2.0) is a hard prerequisite for enabling any paid external API** (DataForSEO, LLM probing, PSI at scale). Controls: per‑workspace limits; daily/monthly cost caps; caching; duplicate‑request prevention; rate limits; plan entitlements; usage metering; admin cost dashboard; alerts; fail‑closed; test/prod separation; request‑explosion protection. **DataForSEO may only be enabled after this exists or is explicitly approved.** *Rationale:* enabling a paid, per‑call external API that user actions/prompts can fan out is a spend‑risk; the existing `ai_usage` metering pattern must be extended to external providers before activation.

## Schema & AI claims (corrected)

- **D9 · ADOPTED — Reject unsupported AI‑markup techniques, using a defensible (non‑absolute) claim.** Verbatim position: *"There is no reliable evidence or documented search‑engine support showing that arbitrary `data-*` attributes, HTML comments, custom AI tags, or CSS class names improve ranking, AI citations, or AI visibility."* Supported approach: standard schema.org, visible content, crawlability, source authority, factual consistency. *Rationale:* the corrected wording avoids the overclaim "impossible for any crawler/model to read" while still rejecting the gimmicks Sempire sells as its premium USP.
- **D10 · ADOPTED — Distinguish three schema levels; never promise a visible feature.** structured‑data implementation → rich‑result eligibility → actual rich‑result appearance (Google decides). Milo delivers the first, can indicate the second, never promises the third.
- **D11 · ADOPTED — Ship the visible TL;DR, reject the `ai-summary` myth.** A visible summary helps readers; the class name carries no documented AI meaning. Milo builds the summary (Article Studio), not the claim that the class does anything.

## Article Studio

- **D12 · ADOPTED — One canonical assembled asset is the sole input to score/preview/export/publish/schema.** No side field is "complete" unless present in the published asset. *Rationale:* removes the entire Potemkin‑field class of defects (faq/cta/internalLinks/schema that neither publish nor score).
- **D13 · ADOPTED — Expanded Article Studio acceptance tests** (16 cases incl. preview/publish parity, source handling, internal‑URL validation, schema‑content consistency, duplicated‑FAQ, missing‑image, alt‑text, mobile, tables, comparison, YMYL, author, refresh, cannibalisation, WordPress/WooCommerce). See `ARTICLE-STUDIO-2.0.md` §7.
- **D‑AS3‑0 · ADOPTED (RESOLVED) — P1.2 id collision resolved: Article Studio 3.0 keeps P1.2; Content Opportunity Engine (M4) → P1.4.** *Owner decision (2026‑07‑21).* Every roadmap/architecture/decision-log reference is renumbered **atomically** so no duplicate or stale P1.2 identity remains (`ROADMAP.md` phase table + §8.5, `TARGET-ARCHITECTURE.md` M4 heading + integrations table, `TRACEABILITY-MATRIX.md`, `AGENCY-BENCHMARK-SEMPIRE.md`, `ARTICLE-STUDIO-2.0.md` cross‑ref). P1.3 is left unassigned by choice.
- **D‑AS3‑1 · ADOPTED — Article Studio 3.0 uses stable anchored presentation blocks OVER composed‑markdown (option A), not a block‑tree canonical model (option B).** *Rationale:* extends the proven 2.0 invariant (one `assembleContentAsset`, one publishable `assembled.{md,html,jsonLd}`); optional JSONB fields ⇒ no migration; preview/publish parity, connector compatibility, and regeneration safety preserved; option B is a rewrite with high migration/parity risk for marginal near‑term gain. **Article Studio 2.0 remains the compatibility foundation** (one ContentAsset, one assembler, one assembled output, one source for preview/export/validation/publishing). Option B **REJECTED for this phase / deferred** — revisit only if the editor outgrows anchored blocks. Full comparison in `ARTICLE-STUDIO-3.0.md` §3.
- **D‑AS3‑2 · ADOPTED — First‑class `hook` and `featuredImage`; a missing featured image, missing featured‑image alt, or missing/unapproved hook is a hard blocker for NEW articles only.** Legacy articles are **never silently broken** — a read‑time `visualState = needsVisualUpgrade` state (no migration, mirrors the `autoPublishApproved` retirement) governs backfill; new blockers apply to new articles or on explicit upgrade. See `ARTICLE-STUDIO-3.0.md` §4/§8.
- **D‑AS3‑3 · ADOPTED — Placement uses stable anchors (before/after‑section:<id>, before‑hook/faq/cta, article‑end) over a PERSISTED section identity (never paragraph numbers, character offsets, heading text, or a hash of the heading); presentation uses bounded enum presets compiled to an allow‑listed HTML/class set (only inline style = clamped `object-position`).** No arbitrary CSS / no unsafe HTML / no absolute positioning / no pixel x/y; stays an article editor, not a page builder. See `ARTICLE-STUDIO-3.0.md` §4.1/§4.2/§9.
- **D‑AS3‑4 · POSTPONED — Custom‑endpoint payload extension (featuredImage/hook/inlineImages/presentation).** Documented as the desired future payload; the connector contract is **unchanged** and must not change without explicit approval. WordPress featured‑media lifecycle and Shopify article‑image replace behaviour are likewise approval‑gated (P1.2G). See `ARTICLE-STUDIO-3.0.md` §7/§12.
- **D‑AS3‑5 · ADOPTED (with open MVP sub‑point) — Legacy→upgraded transition is an explicit author action and forward‑only by default; a documented explicit "revert to legacy policy" escape hatch exists.** New articles (post‑P1.2) require approved hook + approved featured image + alt; legacy articles carry `needsVisualUpgrade`, stay publishable under 2.0 rules, and flip to `current` only on deliberate upgrade. Reverting to `needsVisualUpgrade` is an explicit, logged choice, never an automatic fallback. *Open sub‑decision:* whether to expose the revert control in the MVP or defer it. See `ARTICLE-STUDIO-3.0.md` §8.
- **D‑AS3‑6 · ADOPTED — Stable section‑identity contract.** Each section carries a persisted opaque `id` allocated once; heading text, normalised heading, position, and content hash are **reconciliation signals only**, never the identity. The reconciler resolves unchanged/renamed/moved/merged/split/deleted/regenerated cases and **fails safe** — a semantic replacement is detected and never silently reattached to an unrelated section. See `ARTICLE-STUDIO-3.0.md` §4.1.
- **D‑AS3‑7 · ADOPTED — Broken‑anchor behaviour is severity‑split.** Required image + broken anchor → hard publish blocker (direct resolution). Optional image + broken anchor → warning, excluded from publish until reassigned, never silently moved. Legacy image without an anchor → may map to `article-end` only during the controlled legacy‑upgrade flow, visibly marked as needing placement review. See `ARTICLE-STUDIO-3.0.md` §4.2.
- **D‑AS3‑8 · ADOPTED — One approved Storage object per featured image with presentation VARIANTS (hero/mobile/social crop, aspect, focal, object‑fit) as metadata.** Storage objects are never duplicated because presentation metadata changes; a separate physical social/OG asset is optional, not mandatory; media‑identity + stale‑variant handling on republish is idempotent (`wordpressMediaId`, `publishedObjectHash`) and approval‑gated. See `ARTICLE-STUDIO-3.0.md` §4.3.
- **D‑AS3‑9 · ADOPTED — Hook quality & safety validation.** The hook is visible canonical content, editable, explicitly approved, included exactly once, and consistent across preview/markdown/HTML/connector payloads. Validation **blocks** unsupported statistics/outcomes, fabricated testimonials, guarantees, and YMYL claims without support; **warns** on generic filler, title repetition, off‑topic hooks, excessive clickbait, and excessive length. See `ARTICLE-STUDIO-3.0.md` §4.4.
- **D‑AS3‑10 · ADOPTED — Two‑mode visual composition (Preview + Arrange) over the single canonical asset.** Preview mode = clean, connector‑aware, desktop+mobile reader view. Arrange mode = selectable blocks, stable drop zones, drag‑and‑drop image movement, inline size/align/aspect/crop/focal/caption/alt, inline hook edit+approve, featured crop+focal. Dragging **never** stores pixel coordinates or paragraph indexes — every drop resolves to a stable semantic anchor. The preview is an editing surface over the same `ContentAsset` (no separate preview‑only document/state); Arrange edits update typed fields, mark dirty, use the editor‑wide Save, survive refresh, and feed the canonical assembler with preview/export/publish parity. No absolute positioning / pixel x/y / arbitrary CSS / margins / overlap / unsupported connector layouts. Connector fidelity is reported with the **four‑state model** (generated / included / retained / destination‑verified) and downgrades are shown explicitly. See `ARTICLE-STUDIO-3.0.md` §5.1/§7.
- **D‑AS3‑11 · ADOPTED — Approved implementation order: A → C → D → B → F → E → G → H** (Hook → Stable anchors → Presentation controls → Featured image → Responsive preview → Visual editor → Connector compatibility → Checklist/scoring/legacy backfill). Each sub‑epic: one commit, tests, adversarial review, no migration; P1.2G connector behaviours are approval‑gated. P1.2A implementation does not begin until Article Studio 2.0 is formally closed (it is, 2026‑07‑21) **and** this plan is approved. See `ARTICLE-STUDIO-3.0.md` §11.
